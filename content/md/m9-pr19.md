## Лекция

В КИМ есть отдельный критерий — «безопасность информационной системы». Сегодня мы сами взломаем учебную страницу тремя самыми распространёнными атаками, а потом закроем их в портале. Все опыты — только на своём `localhost`: атаковать чужие сайты незаконно (ст. 272 УК РФ).

## 1. SQL-инъекция

**Суть.** Если данные пользователя вклеить прямо в текст SQL-запроса, пользователь может дописать в запрос свой SQL. База не отличит «ваш» код от «чужого».

Уязвимая страница `practice/sqli.php` (подключается к базе портала):

```php
<?php
require_once 'C:/xampp/htdocs/portal/db.php';   // база портала

$q = $_GET['login'] ?? '';
// ОПАСНО! Данные вклеены в SQL.
$sql = "SELECT login, fio FROM users WHERE login = '$q'";
echo '<p>Запрос: <code>' . e($sql) . '</code></p>';

foreach ($pdo->query($sql) as $row) {
    echo e($row['login']) . ' — ' . e($row['fio']) . '<br>';
}
```

Попробуйте адреса:

- `sqli.php?login=adminka` — нормальная работа, одна строка.
- `sqli.php?login=' OR '1'='1` — запрос становится `WHERE login = '' OR '1'='1'`, условие всегда истинно, выводятся **все** пользователи.
- `sqli.php?login=' UNION SELECT login, password_hash FROM users -- -` (`-- ` начинает комментарий в MySQL, лишний `-` нужен, чтобы браузер не съел пробел) — на экране хеши паролей всех пользователей. Так и «утекают» базы.

**Защита — подготовленные запросы (prepared statements).** SQL отправляется в базу отдельно от данных. Сначала MySQL получает «шаблон» с местами `?`, а данные приходят потом и **всегда** считаются просто значениями, а не кодом.

```php
<?php
$stmt = $pdo->prepare('SELECT login, fio FROM users WHERE login = ?');
$stmt->execute([$q]);
foreach ($stmt as $row) { /* ... */ }
```

Теперь ввод `' OR '1'='1` ищет пользователя с таким странным логином — и не находит. Можно использовать и именованные метки: `WHERE login = :login` и `execute(['login' => $q])`.

**Что нельзя подставить через `?`.** Имена столбцов и таблиц, слова `ASC`/`DESC`. Если сортировка зависит от пользователя (ЛР30), используем **белый список**: массив разрешённых вариантов, а значение пользователя служит только ключом в нём.

**Правило курса:** `$pdo->query()` — только для запросов **без** переменных (например, список услуг). Есть переменная — `prepare()` + `execute()`.

## 2. XSS (межсайтовый скриптинг)

**Суть.** Пользователь вводит не текст, а HTML/JavaScript, а мы выводим его «как есть». Браузер другого человека (например, администратора) выполнит этот скрипт — и злоумышленник может, например, украсть данные или выполнить действия от имени админа.

```php
<?php
// practice/xss.php — ОПАСНО
$name = $_GET['name'] ?? 'гость';
echo "<h1>Привет, $name!</h1>";
```

Откройте `xss.php?name=<script>alert('XSS')</script>` — выскочит окно. Теперь представьте, что такой «адрес» пользователь ввёл в поле заявки, а админ открыл панель со всеми заявками.

**Защита — экранирование при выводе.** `htmlspecialchars()` превращает `<` в `&lt;`, `>` в `&gt;`, кавычки — в `&quot;` и `&#039;`. Браузер покажет символы, но не выполнит их. В портале это наша функция `e()`:

```php
<?php
echo '<h1>Привет, ' . e($name) . '!</h1>';
```

Правила:

- экранируем **при выводе**, а в базу сохраняем как есть;
- экранируем **всё**, что пришло от пользователя или из базы: ФИО, адрес, причину отмены, название «иной услуги», логин в меню, значения в `value="..."`;
- `ENT_QUOTES` обязателен, иначе кавычка в `value` «вырвется» из атрибута.

Дополнительно cookie сессии у нас помечена `httponly` (ЛР23) — даже если XSS где-то проскочит, украсть её через JavaScript не получится.

## 3. CSRF (подделка межсайтового запроса)

**Суть.** Администратор вошёл в портал. В соседней вкладке он открывает «смешную картинку» на чужом сайте. На той странице спрятана форма, которая сама отправляется на **ваш** портал:

```html
<!-- evil.html на чужом сайте -->
<form id="f" method="post" action="http://localhost/portal/admin.php">
    <input type="hidden" name="id" value="1">
    <input type="hidden" name="status" value="cancelled">
    <input type="hidden" name="cancel_reason" value="взлом">
</form>
<script>document.getElementById('f').submit();</script>
```

Браузер админа приложит к запросу свою cookie сессии (при некоторых настройках браузера и сайта), и портал решит, что это сам админ отменил заявку. Пароль злоумышленнику не нужен — он «едет» на чужой сессии.

**Защита — CSRF-токен.** При первом обращении кладём в сессию длинную случайную строку. В каждую POST-форму добавляем её скрытым полем. При обработке формы сверяем: токен из формы должен совпасть с токеном в сессии. Чужой сайт не может прочитать ваш токен, значит, и подделать форму не сможет. Дополнительно помогает атрибут cookie `SameSite=Lax` (он у нас уже стоит), но токен — основная защита.

**Добавляем в `includes/auth.php`:**

```php
<?php
// --- CSRF-защита ---

// Токен текущей сессии (создаётся один раз).
function csrf_token(): string
{
    if (empty($_SESSION['csrf'])) {
        $_SESSION['csrf'] = bin2hex(random_bytes(32));
    }
    return $_SESSION['csrf'];
}

// Скрытое поле для вставки в каждую POST-форму.
function csrf_field(): string
{
    return '<input type="hidden" name="csrf" value="' . e(csrf_token()) . '">';
}

// Проверка токена. Вызывать первой строкой обработки POST.
function check_csrf(): void
{
    $sent = $_POST['csrf'] ?? '';
    if (!is_string($sent) || !hash_equals(csrf_token(), $sent)) {
        http_response_code(400);
        exit('Форма устарела или отправлена с чужого сайта. Обновите страницу и попробуйте снова.');
    }
}
```

- `random_bytes(32)` — криптографически стойкие случайные байты; `rand()` и `uniqid()` для токенов не годятся (предсказуемы).
- `hash_equals()` сравнивает строки за одинаковое время — защита от атак по времени.

**Как подключить к формам.** В каждой POST-форме внутри `<form>` пишем `<?= csrf_field() ?>`, а в обработчике первой строкой — `check_csrf()`:

```php
<?php
// login.php — обработка (фрагмент)
if ($_SERVER['REQUEST_METHOD'] === 'POST') {
    check_csrf();
    $login    = post('login');
    $password = post('password');
    // ... дальше как в ЛР25
}
```

```html
<form method="post" action="login.php">
    <?= csrf_field() ?>
    <!-- поля формы -->
</form>
```

Обратите внимание: в `login.php` после успешного входа мы вызываем `session_regenerate_id(true)` — ID сессии меняется, но данные (и токен) в ней сохраняются, так что формы продолжают работать.

## Сводная памятка «Безопасность портала»

| Угроза | Где в портале | Защита |
|---|---|---|
| SQL-инъекция | Все запросы с данными | `prepare()` + `execute()`, белый список для сортировки |
| XSS | Вывод ФИО, адреса, причины отмены, логина | `e()` при каждом выводе |
| CSRF | Регистрация, вход, новая заявка, смена статуса | `csrf_field()` + `check_csrf()` |
| Утечка паролей | Таблица `users` | `password_hash` / `password_verify` |
| Фиксация сессии | Вход | `session_regenerate_id(true)` |
| Обход прав | `admin.php`, страницы пользователя | `require_admin()`, `require_user()` |
| Чужая заявка | Заявки пользователя | `WHERE user_id = ?` с id из сессии (ЛР28) |

**Связь с экзаменом.** Эксперт по критерию «безопасность ИС» смотрит код и пробует простые атаки: кавычку в поле входа, `<script>` в поле адреса, вход в админку без прав. Подготовленные запросы, экранирование, хеши паролей и проверка ролей — минимум, который должен быть у каждого. CSRF-токен показывает, что вы понимаете безопасность глубже.
