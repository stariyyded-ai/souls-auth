## Лекция

В ЛР25 мы научились входить, но двери пока открыты: любой гость может набрать `localhost/portal/admin.php` и попасть в админку (пусть пока и пустую). Сегодня ставим замки и создаём администратора.

**Авторизация и аутентификация.** Два похожих слова, два разных вопроса:

- **Аутентификация** — «кто ты?» (вход по логину и паролю, ЛР25);
- **Авторизация** — «что тебе можно?» (проверка роли, сегодня).

**Принцип: проверяем на сервере на каждой странице.** Скрытая ссылка в меню — это удобство, а не защита. Экзаменатор обязательно попробует открыть `admin.php`, будучи обычным пользователем, и `requests.php` — будучи гостем. Поэтому каждая закрытая страница в самом начале, **до любой работы и вывода**, вызывает функцию-«охранника».

Карта доступа нашего портала:

| Страница | Гость | Пользователь | Администратор |
|---|---|---|---|
| `register.php`, `login.php` | да | редирект на главную | редирект на главную |
| `requests.php`, `request_new.php` | редирект на вход | да | редирект в админку |
| `admin.php` | редирект на вход | 403 «Доступ запрещён» | да |
| `logout.php`, `index.php` | да | да | да |

Администратор в нашем портале не создаёт заявки сам, поэтому со страниц пользователя мы отправляем его в панель. Если в ТЗ вашего варианта админ тоже может подавать заявки, уберите этот редирект.

**Код 403.** Когда вошедшему пользователю что-то нельзя, правильно ответить HTTP-статусом **403 Forbidden** и понятным текстом. Гостя же логичнее не «ругать», а отправить на вход.

**Дополняем `includes/auth.php`.** Это его полная версия на сегодня (в ПР19 добавим CSRF):

```php
<?php
// includes/auth.php — всё про пользователя: кто вошёл, какая роль, доступ.
require_once __DIR__ . '/../db.php';

function current_user(): ?array
{
    return $_SESSION['user'] ?? null;
}

function is_admin(): bool
{
    return (current_user()['role'] ?? '') === 'admin';
}

// Пускает только вошедших. Гостя отправляет на вход.
function require_login(): void
{
    if (current_user() === null) {
        redirect('login.php');
    }
}

// Пускает только обычных пользователей (админа отправляет в панель).
function require_user(): void
{
    require_login();
    if (is_admin()) {
        redirect('admin.php');
    }
}

// Пускает только администратора.
function require_admin(): void
{
    require_login();
    if (!is_admin()) {
        http_response_code(403);
        $title = 'Доступ запрещён';
        require __DIR__ . '/header.php';
        echo '<div class="alert alert-danger">Доступ запрещён. Эта страница только для администратора.</div>';
        require __DIR__ . '/footer.php';
        exit;
    }
}
```

Использование — одна строка в начале страницы:

```php
<?php
// admin.php — начало
require_once __DIR__ . '/includes/auth.php';
require_admin();

$title = 'Панель администратора';
require __DIR__ . '/includes/header.php';
?>
<h1 class="h3 mb-3"><?= e($title) ?></h1>
<p>Здравствуйте, <?= e(current_user()['fio']) ?>! Здесь будет список всех заявок (ЛР29).</p>
<?php require __DIR__ . '/includes/footer.php'; ?>
```

```php
<?php
// requests.php и request_new.php — начало
require_once __DIR__ . '/includes/auth.php';
require_user();
```

Почему `exit` внутри `require_admin()` так важен? Без него PHP выведет сообщение «Доступ запрещён», а потом… спокойно выполнит остальной код `admin.php` и покажет все заявки ниже. Функция `redirect()` из `config.php` уже содержит `exit`, поэтому в `require_login()` он не нужен отдельно.

**Создаём администратора.** По образцу ТЗ экзамена администратор входит с логином `adminka` и паролем `password`. Через форму регистрации его создать нельзя: регистрация всегда даёт роль `user`, и это правильно. Есть два способа.

*Способ 1. SQL с готовым хешем.* Хеш пароля `password`, полученный через `password_hash()`, можно вставить прямо в базу. Выполните во вкладке SQL phpMyAdmin:

```sql
INSERT INTO users (fio, phone, email, login, password_hash, role)
VALUES ('Администратор', '+7(000)-000-00-00', 'admin@portal.local', 'adminka',
        '$2y$10$B7rmQZdwkiN1Th9I5Jdiw.TT6RdGG0OsNTpFebh.mIJmDw10OYYju', 'admin');
```

*Способ 2. Сгенерировать хеш самому.* Создайте временный файл `hash.php` с одной строкой `<?php echo password_hash('password', PASSWORD_DEFAULT);`, откройте его в браузере, скопируйте результат в поле `password_hash` и **удалите файл**. Ещё вариант: зарегистрировать пользователя `adminka` через форму, а потом в phpMyAdmin поменять ему `role` на `admin` (пароль `password` проходит наше правило «≥ 6 символов»).

Нельзя: вписывать в поле `password_hash` слово `password` открытым текстом — `password_verify()` вернёт `false`, и админ не войдёт. Это одна из самых частых потерь баллов на экзамене: «админка не открывается».

**Отдельный SQL-файл для сдачи.** Строку создания администратора сохраните в файл `database.sql` вашего проекта (вместе с дампом из ЛР20) — тогда при переносе проекта на другой компьютер админ появится автоматически.

**Проверяем «взлом».** Хороший разработчик сам пытается обойти свою защиту:

1. Гостем откройте `admin.php`, `requests.php`, `request_new.php` — каждый раз должна открываться страница входа.
2. Войдите пользователем и откройте `admin.php` — «Доступ запрещён», код 403 (DevTools → Network → Status).
3. Войдите как `adminka` — сразу попадаете в панель, в меню пункт «Панель администратора».
4. Под админом откройте `requests.php` — редирект в панель.
5. Выйдите и нажмите «Назад» в браузере, затем F5 — снова вход.

**Почему гостю — редирект, а пользователю — 403.** Гость, скорее всего, просто ещё не вошёл: логично показать ему форму входа. Пользователь уже вошёл, и его роль известна — отправлять его на вход бессмысленно (он снова войдёт и снова попадёт сюда). Честный ответ «доступ запрещён» с кодом 403 понятен и человеку, и эксперту, который смотрит вкладку Network.

**Правильный порядок строк на любой защищённой странице:**

1. `require_once __DIR__ . '/includes/auth.php';` — функции и база.
2. `require_admin();` или `require_user();` — охранник.
3. Обработка POST (если есть), запросы к базе.
4. `$title = ...; require __DIR__ . '/includes/header.php';` — вывод.

Поменяли местами 2 и 4 — получите `headers already sent`. Поставили охранник после запросов к базе — данные уже прочитаны (и, возможно, изменены) до проверки прав.

**Права на уровне данных.** Охранник отвечает на вопрос «можно ли открыть страницу». Но есть и второй вопрос: «можно ли работать с **этой** записью». Пользователь имеет право открыть `requests.php`, но только со **своими** заявками. Это мы сделаем в ЛР28 условием `WHERE user_id = ?`, а в ЛР31 — проверкой владельца заявки. Помните: защита страницы и защита данных — две разные проверки, нужны обе.

**Типичные ошибки.**

- `require_admin()` вызвана **после** подключения `header.php` — успевает уйти HTML, редирект ломается с `headers already sent`.
- Защита поставлена на `admin.php`, но забыта на `request_new.php` — гость создаёт заявку, а в базе `user_id` пустой (ошибка внешнего ключа).
- Проверка роли через `$_GET['role']` или скрытое поле формы — это не защита.
- Администратор создан, но вход не работает — в `password_hash` записан открытый пароль или хеш с лишним пробелом.
- В `role` записано `Admin` с большой буквы, а код сравнивает с `admin`.

**Связь с экзаменом.** Аспект «безопасность ИС» напрямую проверяет разграничение доступа, а вход `adminka`/`password` — обязательный сценарий проверки. Если админ не входит, эксперт не сможет проверить и всю панель администратора (ЛР29): одна ошибка обнуляет сразу несколько аспектов.

## Если не успел / для сильных

**Минимум для зачёта:** `require_admin()` в `admin.php` и рабочий вход `adminka`/`password`.
**Для сильных:** сделайте единую функцию `require_role(string ...$roles)`, которая принимает список допустимых ролей, и перепишите охранников через неё.
