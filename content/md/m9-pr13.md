## Учебная база данных модуля: `portal_training`

Во всех примерах модуля используется одна и та же учебная БД — портал клининговой компании (вариант «Мой Не Сам»). Преподаватель выдаёт её файлом `portal_training.sql`; ниже — полный текст этого файла. Ваш собственный портал (ваш вариант из сквозного проекта) устроен так же, только услуги и статусы другие.

| Таблица | Что хранит | Связи |

| `services` | справочник услуг с ценой | одна услуга → много заявок |

## Лекция

**С чего начинается любая заявка.** Вы оформляете доставку еды: вводите телефон, адрес, выбираете блюда, способ оплаты. Через минуту курьер видит ваш заказ, кухня видит состав, а вы — статус «Готовится». Всё это возможно потому, что данные лежат не в куче текстовых файлов, а в базе данных, где каждая вещь хранится в своей таблице и таблицы связаны между собой. На экзамене от вас ждут ровно такую же систему, только маленькую: пользователи, услуги, заявки, статусы.

**Реляционная модель — это таблицы.** База данных (БД) — набор таблиц. Таблица описывает один вид объектов: пользователей, услуги, заявки. Строка таблицы (запись) — один конкретный объект: пользователь Иванов. Столбец (поле, атрибут) — одно свойство: логин, телефон, email. Слово «реляционная» происходит от *relation* — «отношение», так в математике называют таблицу. Главное правило: **в одной ячейке — одно значение**. Не «Иванов, +7(912)…» в одной ячейке, а ФИО и телефон в разных столбцах.

Программа, которая хранит таблицы и отвечает на вопросы к ним, называется СУБД. У нас это MySQL (в XAMPP фактически стоит MariaDB — «родная сестра» MySQL, синтаксис тот же). Разговаривают с СУБД на языке **SQL** (Structured Query Language). Команды SQL делятся на группы: **DDL** — описать структуру (`CREATE`, `ALTER`, `DROP`), **DML** — работать с данными (`INSERT`, `SELECT`, `UPDATE`, `DELETE`). Сегодня — DDL.

**Типы данных: что положить в столбец.** У каждого столбца есть тип — он говорит СУБД, какие значения разрешены и сколько места выделять. Минимальный набор для портала заявок:

| Тип | Что хранит | Пример в портале |
|---|---|---|
| `INT` (`INT UNSIGNED`) | целые числа (без знака — только ≥ 0) | `id`, `user_id` |
| `VARCHAR(n)` | строка до *n* символов | логин `VARCHAR(50)`, email `VARCHAR(100)` |
| `TEXT` | длинный текст (до 65 535 байт) | причина отмены, отзыв |
| `DECIMAL(10,2)` | точное число с копейками | цена 2500.00 |
| `DATE` | дата `ГГГГ-ММ-ДД` | дата уборки `2026-10-25` |
| `TIME` | время `ЧЧ:ММ:СС` | `14:00:00` |
| `DATETIME` | дата и время | момент создания заявки |
| `ENUM('a','b')` | одно значение из списка | роль `'user'`/`'admin'` |
| `TINYINT(1)` / `BOOLEAN` | 0 или 1 | «заблокирован» да/нет |

Три правила, которые экономят баллы. Первое: **телефон — это строка, а не число**. В `+7(912)-345-67-89` есть скобки и дефисы, а у числа потерялся бы ведущий ноль и знак плюс. Второе: **деньги — `DECIMAL`, а не `FLOAT`**: `FLOAT` хранит числа приближённо, и 0.1 + 0.2 у него не равно 0.3 — для цены это недопустимо. Третье: **пароль — `VARCHAR(255)`**, потому что хранить мы будем не пароль, а его хеш из `password_hash()` (60 символов сейчас, может стать длиннее в будущих версиях PHP).

**CREATE TABLE.** Создадим справочник услуг:

```sql
CREATE TABLE services (
    id    INT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    name  VARCHAR(100) NOT NULL UNIQUE,
    price DECIMAL(10,2) NOT NULL DEFAULT 0
) ENGINE=InnoDB;
```

Разберём по словам:

- `PRIMARY KEY` — **первичный ключ**: столбец, который однозначно определяет строку. Как номер паспорта: двух одинаковых быть не может, пустым быть не может.
- `AUTO_INCREMENT` — СУБД сама выдаёт номер 1, 2, 3… При добавлении записи `id` можно не указывать.
- `NOT NULL` — поле обязательно. `NULL` в SQL — это «значение неизвестно», а не ноль и не пустая строка.
- `UNIQUE` — в столбце не может быть двух одинаковых значений. Для логина это прямо требование ТЗ: «логин уникальный».
- `DEFAULT 0` — значение по умолчанию, если при вставке его не указали.
- `ENGINE=InnoDB` — «движок» хранения. Только InnoDB поддерживает внешние ключи и транзакции; в XAMPP он стоит по умолчанию, но писать его явно — хорошая привычка.

**Внешний ключ — связь между таблицами.** В заявке нужно указать, кто её оставил. Можно было бы скопировать в заявку ФИО и телефон пользователя, но тогда при смене телефона пришлось бы править сто заявок. Поэтому в заявке храним только номер пользователя — `user_id`, а СУБД следит, чтобы такой пользователь существовал. Это и есть **внешний ключ** (FOREIGN KEY):

```sql
CREATE TABLE requests (
    id         INT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    user_id    INT UNSIGNED NOT NULL,
    service_id INT UNSIGNED NOT NULL,
    -- ...остальные поля...
    CONSTRAINT fk_requests_user FOREIGN KEY (user_id)
        REFERENCES users (id) ON DELETE CASCADE ON UPDATE CASCADE,
    CONSTRAINT fk_requests_service FOREIGN KEY (service_id)
        REFERENCES services (id) ON DELETE RESTRICT ON UPDATE CASCADE
) ENGINE=InnoDB;
```

Связь «один пользователь — много заявок» называется **1:N** (один ко многим). Таблица `users` — родительская, `requests` — дочерняя. Внешний ключ всегда живёт в дочерней таблице, на стороне «много».

Что делать с заявками, если удалили родителя? Это задают правила:

- `ON DELETE RESTRICT` — запретить удаление услуги, пока на неё есть заявки (MySQL выдаст ошибку `#1451`). Подходит для справочников: нельзя «потерять» услугу у оформленных заявок.
- `ON DELETE CASCADE` — удалить вместе с родителем все дочерние записи. Удалили пользователя — удалились его заявки.
- `ON DELETE SET NULL` — обнулить ссылку (тогда столбец должен допускать `NULL`).

Важно: **тип внешнего ключа должен совпадать с типом первичного ключа**, на который он ссылается, вплоть до `UNSIGNED`. `INT` и `INT UNSIGNED` — разные типы, и MySQL ответит загадочной ошибкой `#1005 … errno: 150 "Foreign key constraint is incorrectly formed"`. Это самая частая ошибка новичков в этой теме.

Порядок создания таблиц тоже важен: сначала родительские (`users`, `services`, `statuses`), потом `requests`. Нельзя сослаться на таблицу, которой ещё нет.

**Кодировка.** Базу создаём так:

```sql
CREATE DATABASE portal CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
```

`utf8mb4` — полноценный UTF-8: кириллица, буква «ё» и даже эмодзи в отзыве. Старая `utf8` в MySQL хранит не все символы, а `latin1` вместо ФИО покажет знаки вопроса. Сравнение `utf8mb4_unicode_ci` — регистронезависимое: `'Иванов' = 'иванов'` даёт истину.

**Изменить и удалить структуру.**

```sql
ALTER TABLE services ADD COLUMN description TEXT NULL;   -- добавить столбец
ALTER TABLE services MODIFY price DECIMAL(12,2) NOT NULL; -- изменить тип
DROP TABLE services;                                       -- удалить таблицу целиком
```

`DROP` не спрашивает «вы уверены?» и не кладёт в корзину. Сначала думаем, потом нажимаем.

**Типичные ошибки:**

1. Телефон типа `INT` — теряется «+» и скобки, а длинный номер не влезает.
2. `FLOAT` для цены.
3. Нет `UNIQUE` на логине — на экзамене регистрация с уже занятым логином пройдёт, а это потеря балла.
4. Внешний ключ `INT`, а первичный `INT UNSIGNED` — ошибка 150.
5. Статус хранится текстом прямо в заявке («новая», «Новая», «новая » с пробелом) вместо ссылки на справочник `statuses`.
6. Запятая после последнего столбца перед `)` — синтаксическая ошибка `#1064`.

**Связь с экзаменом.** В задании 1 вы создаёте БД портала, в задании 3 сдаёте её диаграмму. Эксперт откроет phpMyAdmin и посмотрит: есть ли первичные ключи, связаны ли таблицы внешними ключами, разумны ли типы, уникален ли логин. Хорошая структура — это половина модуля «Проектирование ИС», и делается она за 15–20 минут, если вы знаете эти 6 типов и 3 вида ключей.

```sql
CREATE TABLE clients (
    id INT AUTO_INCREMENT PRIMARY KEY,
    login VARCHAR(50) NOT NULL,
    phone INT NOT NULL,
    balance FLOAT,
);
CREATE TABLE bookings (
    id INT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    client_id INT UNSIGNED NOT NULL,
    status VARCHAR(20),
    FOREIGN KEY (client_id) REFERENCES clients (id)
);
```

**Ход работы:**

1. Запустите XAMPP (Apache + MySQL), откройте phpMyAdmin, создайте пустую базу `pr13_autoservice` с сравнением `utf8mb4_unicode_ci`.
2. В тетради или в файле `pr13.md` выпишите сущности из описания заказчика (подсказка: их 5) и для каждой — поля.
3. Заполните таблицу «поле — тип — почему»: минимум для полей `login`, `phone`, `price`, `visit_date`, `visit_time`, `car_number`, `cancel_reason`, `role`.
4. Найдите во фрагменте DDL выше все ошибки (их не меньше пяти), выпишите их и исправьте.
5. На вкладке SQL базы `pr13_autoservice` напишите и выполните `CREATE TABLE` для всех пяти таблиц. Порядок: сначала справочники, потом клиенты, потом записи.
6. Проверьте ограничения на практике. Выполните и запишите, какая ошибка получилась и почему:
   ```sql
   INSERT INTO clients (login, password, full_name, phone, email)
   VALUES ('test01', 'x', 'Тест Тестов', '+7(900)-111-11-11', 't@t.ru');
   INSERT INTO clients (login, password, full_name, phone, email)
   VALUES ('test01', 'y', 'Другой Человек', '+7(900)-222-22-22', 'd@t.ru');
   ```
   (вторая вставка должна упасть с ошибкой `#1062 Duplicate entry`; если не упала — у вас нет `UNIQUE` на логине).
7. Добавьте командой `ALTER TABLE` в таблицу услуг столбец `duration_min SMALLINT UNSIGNED NULL` (длительность в минутах).
8. Откройте вкладку «Структура» → «Связи» (Relation view) у таблицы записей и убедитесь, что внешние ключи видны.

## Критерии оценки

| Аспект | 2 балла | 1 балл | 0 баллов |
|---|---|---|---|
| Состав таблиц | 5 таблиц, справочники вынесены отдельно | 4 таблицы или статус хранится текстом | меньше 4 таблиц |
| Типы данных | все поля с разумными типами (телефон — строка, цена — DECIMAL, дата — DATE) | 1–2 неудачных типа | 3 и более ошибок в типах |
| Ключи | PK во всех таблицах, UNIQUE на логине, все FK созданы | нет UNIQUE или одного FK | FK отсутствуют |
| Разбор ошибочного DDL | найдено и исправлено ≥ 5 ошибок | 3–4 ошибки | меньше 3 |
| Скрипт выполняется | `pr13.sql` выполняется на чистой БД без ошибок | выполняется после 1 правки | не выполняется |
