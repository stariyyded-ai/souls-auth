## Лекция

**Документация — это не «бумажки для препода».** Подумайте, что будет с вашим порталом через три месяца. Вы в модуле 5 пишете админ-панель и не помните, какие статусы договорились использовать и как называется поле с причиной отмены. Или вы заболели, а проект продолжает однокурсник. Или на собеседовании просят: «Покажите, как вы проектировали систему». Во всех случаях нужен короткий, аккуратный пакет документов, где всё решено один раз и записано. Сегодня собираем такой пакет для своего варианта из того, что уже наработано в ПР1–ЛР3.

На экзамене полноценный пакет никто не пишет, но его «сжатая версия» (чек-лист требований на черновике, карта страниц, диаграмма БД) — то, с чего выгодно начинать. А ER-диаграмма — прямой артефакт задания 3. Кто сделал документацию на своём проекте, на экзамене воспроизведёт её за 15 минут.

**Состав пакета (папка `docs/` в репозитории):**

```
portal/docs/
├── README.md            ← оглавление пакета
├── tz.md                ← ТЗ-лист (1–2 страницы)
├── sitemap.drawio       ← карта сайта (исходник)
├── sitemap.png          ← карта сайта (картинка)
├── er.drawio / er.png   ← ER-диаграмма (из ЛР3)
├── usecases.md          ← 3 ключевых сценария с альтернативами (из ПР2)
└── trace.md             ← матрица трассировки требований
```

**ТЗ-лист: что в нём должно быть.** Не переписывайте ТЗ преподавателя слово в слово — переведите его в *проверяемые* требования с номерами. Шаблон:

```markdown
# ТЗ-лист: портал заявок «Починим»

## 1. Общие сведения
Заказчик: сервис ремонта техники «Починим».
Цель: приём заявок на ремонт онлайн и их обработка мастером.
Стек: PHP 8.2, MySQL/MariaDB (utf8mb4), HTML/CSS, Bootstrap 5, JavaScript.

## 2. Роли
| Роль | Доступ |
| Гость | регистрация, вход |
| Клиент | создание заявки, свои заявки, выход |
| Администратор (adminka / password) | все заявки, смена статуса, причина отклонения, стоимость |

## 3. Функциональные требования
ФТ-01 Регистрация с полями: логин, пароль, ФИО, телефон, email.
ФТ-02 Логин уникален; при совпадении — сообщение «Логин занят».
ФТ-03 Вход по логину и паролю; при ошибке — «Неверный логин или пароль».
ФТ-04 После входа клиент попадает на «Мои заявки», администратор — в админ-панель.
...
ФТ-12 При статусе «Отклонено» причина обязательна.

## 4. Требования к данным и валидации
| Поле | Правило | Пример верного значения |
| Логин | латиница и цифры, ≥ 6 | master1 |
| ФИО | кириллица и пробелы | Иванов Иван Иванович |
| Телефон | +7(XXX)-XXX-XX-XX | +7(912)-345-67-89 |
| Email | формат email | ivan@mail.ru |
| Пароль | ≥ 6 символов | qwerty1 |

## 5. Нефункциональные требования
НФТ-01 Мобильная версия: все страницы корректны при ширине 390 px (макет 390×844).
НФТ-02 Пароли хранятся только в виде хеша.
НФТ-03 Страницы клиента и админа недоступны без входа и с чужой ролью.
НФТ-04 Кодировка UTF-8 во всех файлах и в БД (utf8mb4).

## 6. Справочники
Статусы: Новая, Диагностика, В ремонте, Готово к выдаче, Отклонено.
Виды техники: Смартфон, Ноутбук, Планшет, Другое.

## 7. Страницы
См. sitemap.png.
```

Свойства хорошего требования:

- **Атомарное** — одно требование, одна проверка. «Регистрация и вход работают» — это два требования.
- **Проверяемое** — на него можно ответить «да» или «нет». «Сайт должен быть удобным» — непроверяемо. «На каждой странице клиента есть ссылка "Выйти"» — проверяемо.
- **С номером** — чтобы ссылаться: «ФТ-07 не выполнено».
- **Без выдумок.** Не добавляйте того, чего нет в ТЗ, и помечайте свои решения отдельно («Решение разработчика: роль хранится в таблице roles»).

**Нумерация требований на экзамене.** Перепишите ТЗ на черновик короткими строками с номерами — это и есть ТЗ-лист. Когда в конце будете проверять себя, идёте по номерам, а не перечитываете две страницы текста.

**Карта сайта в draw.io.** Перерисуйте бумажную карту из ПР2 начисто для своего варианта:

- прямоугольники — страницы, подпись: имя файла и название (`orders.php — Мои заявки`);
- цветом или контейнерами покажите зоны доступа: гость / клиент / админ;
- сплошная стрелка — переход по ссылке или кнопке, пунктирная — автоматический редирект (после входа, после отправки формы, при попытке открыть чужую страницу);
- `logout.php` и обработчики форм без интерфейса можно рисовать скруглённым прямоугольником или подписью «действие».

**Матрица трассировки.** Простая таблица, которая связывает требования с местами в системе. Она отвечает на вопрос эксперта «где это реализовано?» и показывает дыры: требование есть, а страницы или поля для него нет.

| Требование | Страница | Таблица.поле | Как проверить |
|---|---|---|---|
| ФТ-02 Уникальный логин | register.php | users.login UNIQUE | Зарегистрировать двух пользователей с одним логином → сообщение |
| ФТ-04 Редирект по роли | login.php → orders.php / admin.php | users.role_id | Войти клиентом и админом |
| ФТ-12 Причина отклонения | admin.php | orders.cancel_reason | Выбрать «Отклонено» без причины → ошибка |
| НФТ-02 Хеш пароля | register.php | users.password VARCHAR(255) | В phpMyAdmin пароль вида `$2y$10$...` |

Столбец «Как проверить» — готовый сценарий тестирования для модулей 5–6 и для пробного экзамена.

**README.md пакета** — оглавление: перечень файлов, одна строка о каждом, дата последнего обновления, версия.

**Согласованность — главное качество пакета.** Все документы описывают одну и ту же систему. Названия страниц в ТЗ-листе, на карте сайта и в матрице совпадают. Каждое поле из таблицы валидации есть на ER-диаграмме. Статусы в ТЗ-листе и в справочнике `statuses` одинаковы. Самая частая потеря качества — не отсутствие документа, а противоречия между документами.

**Markdown за 2 минуты.** Документы пишем в Markdown: GitHub красиво его показывает, а VS Code даёт предпросмотр (Ctrl+Shift+V). Нужно знать: `#` — заголовок, `-` — пункт списка, `|` — таблица, `**жирный**`, `` `код` ``, картинка: `![ER-диаграмма](er.png)`.

**Типичные ошибки:**

- ТЗ-лист — копия текста задания без номеров и разбиения: проверять по нему невозможно.
- Требования «вообще»: «система должна быть безопасной». Перепишите как НФТ-02 и НФТ-03 из примера.
- Карта сайта и ER-диаграмма сделаны для «Мой Не Сам», а вариант — кафе.
- В документах всё есть, но в Git попали только `.drawio` без PNG — на GitHub картинка не видна.
- Пакет «сделали и забыли». Документацию обновляют при изменениях; в модулях 4–5 вы будете возвращаться к ER-диаграмме.

## Задание

**Цель:** собрать согласованный пакет проектной документации своего портала и зафиксировать его в репозитории как версию 0.1.

**Исходные данные:** ваш вариант; результаты ПР1 (разбор ТЗ), ПР2 (сценарии, карта сайта), ЛР3 (ER-диаграмма), ПР4 (нормализация); репозиторий из ЛР2.

**Ход работы:**

1. (5 мин) Создайте в репозитории ветку `docs/v0.1` и структуру `docs/` из лекции.
2. (25 мин) Напишите `docs/tz.md` по шаблону: не меньше 12 функциональных требований с номерами, таблица валидации, 3–4 нефункциональных требования, справочники, решения разработчика.
3. (20 мин) Нарисуйте карту сайта в draw.io: страницы с именами файлов, зоны доступа, ссылки и редиректы. Экспортируйте `sitemap.png`.
4. (5 мин) Перенесите из ПР2 в `docs/usecases.md` три ключевых сценария своего варианта (с альтернативами).
5. (5 мин) Сверьте ER-диаграмму с ПР4: модель в 3НФ, правила `ON DELETE` подписаны у связей. Исправьте и переэкспортируйте `er.png`.
6. (15 мин) Составьте `docs/trace.md`: каждое ФТ и НФТ → страница → таблица.поле → как проверить.
7. (5 мин) **Взаимопроверка.** Обменяйтесь ссылками на репозиторий с соседом. Он находит в вашем пакете минимум одно противоречие или пропуск и пишет его в Issues на GitHub (или на листке). Исправьте.
8. (5 мин) Напишите `docs/README.md` (оглавление с картинками `sitemap.png` и `er.png`), закоммитьте, влейте ветку в `main`, поставьте тег и отправьте:

```bash
git switch main
git merge docs/v0.1
git tag -a v0.1 -m "Проектная документация"
git push && git push --tags
```

**Что сдать:** ссылку на репозиторий с тегом `v0.1`; в `docs/` — `README.md`, `tz.md`, `sitemap.png` (+ `.drawio`), `er.png` (+ `.drawio`), `usecases.md`, `trace.md`; отметку о взаимопроверке (Issue или лист).

## Критерии оценки

| Аспект | 2 балла | 1 балл | 0 баллов |
|---|---|---|---|
| ТЗ-лист | ≥ 12 атомарных проверяемых ФТ с номерами, валидация, НФТ, справочники | Требования не пронумерованы или есть размытые | Копия задания или отсутствует |
| Карта сайта | Все страницы, зоны доступа, переходы и редиректы, нет тупиков | 1–2 пропуска | Не по варианту или отсутствует |
| ER-диаграмма | 3НФ, PK/FK, связи и правила целостности, соответствует ТЗ-листу | Мелкие расхождения с ТЗ-листом | Отсутствует |
| Трассировка | Все требования связаны со страницей, полем и способом проверки | Покрыта половина требований и больше | Меньше половины |
| Согласованность | Названия и данные во всех документах совпадают | 1–2 противоречия | Документы противоречат друг другу |
| Репозиторий | Всё в `docs/`, PNG видны на GitHub, тег `v0.1` | Нет тега или части файлов | Не выложено |
