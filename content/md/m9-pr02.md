## Лекция

**Проблема: «страницы есть, а сайт не работает».** На ПР1 мы получили список страниц. Но список — ещё не сайт. Студент верстает `login.php` и `orders.php`, а потом выясняется, что после регистрации пользователь попадает на пустую страницу, из админки нет кнопки «Выйти», а после создания заявки форма просто очищается, и человек не понимает, отправилась она или нет. Каждая страница по отдельности хороша, а *путь* по ним сломан. Сценарии и карта сайта нужны, чтобы увидеть путь до того, как вы написали хоть строчку кода.

Пример из жизни: вы заказываете такси в приложении. Открыли, ввели адрес, выбрали тариф, нажали «Заказать», увидели машину на карте. Если после «Заказать» вас выкинет на главный экран без сообщения, вы закажете второй раз. Это ошибка не дизайна кнопки, а сценария.

**Три инструмента, от общего к частному.**

**1. Диаграмма прецедентов (use case).** Отвечает на вопрос «Кто что может делать в системе?». Это стандартная диаграмма из UML. Элементы:

- **Актёр** (человечек) — роль: Гость, Клиент, Администратор;
- **Прецедент** (овал) — действие, которое даёт результат: «Зарегистрироваться», «Создать заявку»;
- **Граница системы** (прямоугольник) — внутри овалы, снаружи актёры;
- **Связь** — линия от актёра к прецеденту;
- **«include»** — прецедент *всегда* включает другой: «Изменить статус» включает «Войти»;
- **«extend»** — *иногда* расширяет: «Отменить заявку» расширяет «Изменить статус» и требует «Указать причину».

Текстовая версия для «Мой Не Сам»:

```
[Гость] ──── (Зарегистрироваться)
[Гость] ──── (Войти)
[Клиент] ─── (Создать заявку)
[Клиент] ─── (Просмотреть свои заявки)
[Клиент] ─── (Выйти)
[Администратор] ── (Просмотреть все заявки)
[Администратор] ── (Изменить статус заявки)
                        ▲ «extend»
                  (Указать причину отмены)
[Администратор] ── (Выйти)
```

Правило: прецедент называется **глаголом** и описывает цель пользователя. «Нажать кнопку» — не прецедент, «Кнопка» тем более. «Создать заявку» — прецедент.

**2. Пользовательский сценарий (user story / сценарий использования).** Это текст, который описывает один прецедент шаг за шагом: основной путь и альтернативы (ошибки). Шаблон:

```
Сценарий: Регистрация клиента
Актёр: Гость
Предусловие: пользователь не вошёл в систему
Основной поток:
  1. Гость открывает страницу регистрации.
  2. Вводит логин, пароль, ФИО, телефон, email.
  3. Нажимает «Зарегистрироваться».
  4. Система проверяет данные и создаёт пользователя.
  5. Система перенаправляет на страницу входа с сообщением «Регистрация успешна».
Альтернативы:
  4а. Логин занят → сообщение «Такой логин уже существует», введённые поля сохраняются.
  4б. ФИО содержит латиницу → сообщение у поля ФИО.
  4в. Телефон не в формате +7(XXX)-XXX-XX-XX → сообщение у поля телефона.
Результат: в БД новая запись пользователя с ролью «клиент».
```

Обратите внимание на **альтернативы**. Именно их чаще всего забывают, а на экзамене эксперт специально вводит неверные данные. Если в ТЗ сказано «сообщение о неверных данных», в сценарии это должно быть отдельной строкой. Удобная формула для поиска альтернатив: «А что, если пользователь ввёл неправильно / оставил пустым / уже существует / нет прав?»

Короткая форма — **user story** в стиле agile: «Как *клиент*, я хочу *видеть статус своей заявки*, чтобы *не звонить в компанию*». Её удобно писать на карточках, но для экзамена полезнее развёрнутый сценарий с альтернативами.

**3. User flow (поток пользователя).** Блок-схема одного пути через экраны: прямоугольник — экран, ромб — решение или проверка, стрелка — переход. Пример для создания заявки:

```
[Вход] → <данные верны?> ─нет→ [Вход + ошибка]
               │да
               ▼
        <роль = админ?> ─да→ [Админ-панель]
               │нет
               ▼
        [Мои заявки] → (Новая заявка) → [Форма заявки]
                                             │ Отправить
                                             ▼
                                    <поля заполнены верно?> ─нет→ [Форма + ошибки]
                                             │да
                                             ▼
                              [Мои заявки + «Заявка создана», статус «Новая»]
```

User flow хорошо показывает **тупики** (экран, с которого некуда уйти) и **лишние шаги**.

**4. Карта сайта (sitemap).** Схема всех страниц и связей между ними, сгруппированная по доступу. Это вид «сверху»: user flow — одна дорога, карта сайта — карта города.

```
                    ┌──────────────┐
                    │  index.php   │  (редирект: гость → login, клиент → orders, админ → admin)
                    └──────┬───────┘
          ┌────────────────┴───────────────┐
   ГОСТЬ  ▼                                ▼
  ┌──────────────┐   ссылка   ┌──────────────┐
  │ register.php │ ◄────────► │  login.php   │
  └──────────────┘            └──────┬───────┘
                         ┌───────────┴─────────────┐
  КЛИЕНТ                 ▼                АДМИН     ▼
  ┌──────────────┐  ┌──────────────┐      ┌──────────────┐
  │  orders.php  │◄►│order_new.php │      │  admin.php   │
  └──────┬───────┘  └──────────────┘      └──────┬───────┘
         └──────────────► logout.php ◄───────────┘
```

На карте сайта обязательно указываются: все страницы, кто их видит, переходы и **редиректы** (автоматические переходы после действия). Редиректы — важная деталь для PHP: после успешной отправки формы правильно перенаправить пользователя (приём PRG, Post/Redirect/Get, разберём в модуле 5), иначе обновление страницы отправит заявку повторно.

**Чем рисовать.** На бумаге: быстро и нормально для практики. В **draw.io** (app.diagrams.net или десктоп-версия): есть библиотека UML с актёром и овалами, есть блоки для flowchart. В **Figma/FigJam**: удобно для user flow, если потом рисовать макеты. В этом курсе основной инструмент схем — draw.io, его же используем для ER-диаграммы в ЛР3.

**Проверка «пальцем».** Готовую карту сайта проверяют быстро: положите палец на `index.php` и «пройдите» сайт по очереди за каждую роль. Гость: может ли он зарегистрироваться, а потом войти? Клиент: создать заявку, увидеть её в списке, выйти? Администратор: попасть в админку сразу после входа, сменить статус, отменить заявку с причиной, выйти? Если палец где-то застрял (нет стрелки дальше), вы нашли тупик. Если какой-то прецедент из use case не встретился ни разу, на карте не хватает страницы или действия. Отдельно спросите себя: что увидит клиент, если вручную наберёт в адресной строке `admin.php`? Правильный ответ — редирект на вход или на свои заявки, и эту стрелку тоже стоит нарисовать.

**Связь с экзаменом.** Отдельно use case на экзамене не оценивают, но:

- в **задании 2** нужно нарисовать мобильный дизайн *всех* страниц. Карта сайта — готовый список экранов, ни один не потеряется;
- критерии «разработка модулей ИС по ТЗ» и «интерфейс по ТЗ» проверяют, что всё связано: после входа админ попадает в админку, есть выход, есть сообщения об ошибках. Это ровно альтернативные потоки ваших сценариев;
- user flow экономит время: пишете код по схеме, а не вспоминаете, «куда редиректить».

**Типичные ошибки:**

- Прецеденты названы существительными («Регистрация», «Админка») или технически («Отправить POST-запрос»).
- В сценарии только «счастливый путь», ни одной альтернативы.
- На карте сайта нет `logout` и редиректа после входа: непонятно, как админ попадает в админку.
- Тупик: на странице «Новая заявка» нет ссылки назад к списку.
- Use case, user flow и карта сайта противоречат друг другу: на одной схеме админ создаёт заявки, на другой нет.

## Задание

**Цель:** спроектировать поведение портала: кто что делает, как ходит по страницам и что видит при ошибке.

**Исходные данные:** ваш разбор ТЗ-2 «Починим» из ПР1 (роли, страницы, правила). Если ПР1 не сдан, используйте ТЗ «Мой Не Сам» из лекции ПР1.

**Ход работы:**

1. (15 мин) Нарисуйте use case диаграмму для ТЗ-2: 3 актёра, не меньше 7 прецедентов, граница системы, хотя бы одна связь «include» или «extend» (подсказка: «Отклонить заявку» → «Указать причину»).
2. (25 мин) Напишите по шаблону из лекции три сценария: «Регистрация», «Создание заявки», «Смена статуса администратором». В каждом не меньше 2 альтернативных потоков.
3. (15 мин) Нарисуйте user flow для сценария «Вход → создание заявки», с проверками (ромбами) и ветками ошибок.
4. (15 мин) Нарисуйте карту сайта ТЗ-2: все страницы, группировка по ролям, переходы, редиректы после входа, выхода и отправки форм.
5. (10 мин) Проверьте схемы друг с другом: каждый прецедент есть на карте сайта как страница или действие; на карте нет тупиков. Исправьте найденное.
6. (10 мин) Ответьте письменно: какие сообщения пользователю (успех и ошибки) должны быть в системе? Составьте список из минимум 8 сообщений с точным текстом.

Можно работать на бумаге или в draw.io (тогда сохраните `.drawio` и PNG).

**Что сдать:** use case диаграмму; 3 сценария; user flow; карту сайта; список сообщений системы. Фото листов или файлы.

## Критерии оценки

| Аспект | 2 балла | 1 балл | 0 баллов |
|---|---|---|---|
| Use case | 3 актёра, ≥ 7 прецедентов-глаголов, граница, include/extend | Неполная или неверные названия прецедентов | Отсутствует |
| Сценарии | 3 сценария, у каждого предусловие, основной поток, ≥ 2 альтернативы | Альтернатив меньше или нет одного сценария | Меньше 2 сценариев |
| User flow | Экраны, решения и ветки ошибок обозначены верно | Нет веток ошибок | Отсутствует |
| Карта сайта | Все страницы, роли, переходы, редиректы, нет тупиков | 1–2 пропуска (часто нет logout) | Не соответствует ТЗ |
| Согласованность | Схемы не противоречат друг другу и ТЗ | 1 противоречие | Несколько противоречий |
