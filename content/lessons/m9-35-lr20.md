## Лекция

**Дамп — это «сохранить как» для базы.** Ваши фотографии лежат в облаке, чтобы не пропасть вместе с телефоном. База данных тоже может пропасть: переустановили XAMPP, сменили компьютер в аудитории, случайно выполнили `DROP`. Спасает **дамп** — текстовый файл `.sql` со всеми командами, нужными, чтобы собрать базу заново: `CREATE TABLE` для структуры и `INSERT` для данных. Учебная `portal_training.sql`, которую вы импортируете с первого занятия модуля, — это и есть дамп.

Зачем дамп на экзамене? Результат работы сдаётся файлами: эксперт должен иметь возможность развернуть вашу базу у себя и проверить систему. Без файла БД работающий сайт на вашем компьютере превращается в «у меня всё работало». Кроме того, дамп — страховка в течение самого экзамена: сделали базу — выгрузили; сломали — за 30 секунд вернули.

**Экспорт в phpMyAdmin.** Выберите базу слева → вкладка «Экспорт».

- **Быстрый** способ: формат SQL → «Вперёд». Скачается файл со структурой и данными. Для повседневной страховки этого достаточно.
- **Обычный** способ («отображать все возможные настройки») — для «чистового» дампа на сдачу. Что проверить:
  1. «Таблицы» — выбраны все, у каждой отмечены «Структура» и «Данные».
  2. «Вывод» — «Сохранить вывод в файл», кодировка `utf-8`, сжатие — «Нет» (эксперту удобнее открыть обычный `.sql`).
  3. «Формат» — SQL.
  4. «Параметры создания объектов» — отметьте «Добавить выражение DROP TABLE / VIEW / …»: тогда повторный импорт не упадёт с ошибкой «таблица уже существует». Если в вашей версии есть пункт «Добавить выражение CREATE DATABASE / USE» — отметьте и его, тогда файл сам создаст базу с нужным именем.
  5. «Параметры создания данных» — «Вставлять несколько строк в одном INSERT»: файл получится короче.

Откройте получившийся файл в VS Code и найдите знакомые вещи: `CREATE TABLE` с `ENGINE=InnoDB DEFAULT CHARSET=utf8mb4`, блоки `INSERT INTO`, а внизу — раздел с `ALTER TABLE … ADD CONSTRAINT … FOREIGN KEY`. phpMyAdmin нарочно добавляет внешние ключи **в конце**, после всех данных: так при импорте не важно, в каком порядке идут таблицы.

Альтернатива для любителей консоли (XAMPP → Shell):

```
mysqldump -u root --databases portal_ivanov --default-character-set=utf8mb4 > portal_ivanov.sql
```

Ключ `--databases` добавляет в файл `CREATE DATABASE` и `USE`.

**Дамп считается сделанным, только когда он проверен.** Файл, который не разворачивается, хуже, чем никакого: вы на него рассчитываете, а он подводит. Проверка простая:

1. Создайте пустую базу `portal_check` (`utf8mb4_unicode_ci`).
2. Откройте её → «Импорт» → ваш дамп → «Вперёд». Если в дампе есть `CREATE DATABASE`/`USE`, он развернётся в базу с исходным именем, — тогда для проверки скопируйте файл и удалите из копии эти две строки.
3. Сравните количество строк в оригинале и копии одним запросом:

```sql
SELECT 'users' AS t, COUNT(*) FROM users
UNION ALL SELECT 'services', COUNT(*) FROM services
UNION ALL SELECT 'statuses', COUNT(*) FROM statuses
UNION ALL SELECT 'payment_types', COUNT(*) FROM payment_types
UNION ALL SELECT 'requests', COUNT(*) FROM requests;
```

Для `portal_training` эталон: 7, 5, 4, 2, 15. Обратите внимание: число строк в списке таблиц phpMyAdmin для InnoDB показывается **приблизительно** (со знаком «~»), поэтому сверяем только `COUNT(*)`.

4. Проверьте кириллицу в «Обзоре» и связи в «Дизайнере» копии.

**Диаграмма базы данных.** По плану ДЭ в задании 3 нужна диаграмма БД. В ЛР3 вы рисовали ER-диаграмму **до** создания базы — это был план. Теперь нужна диаграмма **по факту**: какие таблицы, поля, типы и связи реально получились. Два удобных инструмента.

**Способ 1. «Дизайнер» phpMyAdmin.** База → «Ещё» → «Дизайнер». Таблицы показываются карточками, связи — линиями от внешнего ключа к первичному. Что сделать:

- расставить таблицы: `requests` в центр, справочники вокруг, чтобы линии не пересекались;
- кнопкой «Показать/скрыть только ключи» (иконка с ключом) — показать все поля;
- сохранить: в меню Дизайнера есть «Экспорт схемы» (форматы PDF и SVG). Для работы этой функции и сохранения расположения таблиц phpMyAdmin использует служебную базу `phpmyadmin`; в XAMPP она обычно уже настроена. Если появилось сообщение про «хранилище конфигурации phpMyAdmin» — не тратьте время, сделайте аккуратный скриншот окна Дизайнера (Win+Shift+S) и сохраните как PNG.

**Способ 2. dbdiagram.io (язык DBML).** Сайт `dbdiagram.io` рисует диаграмму по короткому текстовому описанию. Плюс — красиво и быстро правится; минус — нужен интернет и описание пишется вручную (впрочем, оно очень похоже на `CREATE TABLE`). Описание учебной базы:

```
Enum user_role {
  user
  admin
}

Table users {
  id int [pk, increment]
  login varchar(50) [not null, unique]
  password varchar(255) [not null, note: 'хеш password_hash()']
  full_name varchar(150) [not null]
  phone varchar(20) [not null]
  email varchar(100) [not null]
  role user_role [not null, default: 'user']
  created_at datetime [not null, default: `now()`]
}

Table services {
  id int [pk, increment]
  name varchar(100) [not null, unique]
  price decimal(10,2) [not null, default: 0]
}

Table statuses {
  id int [pk, increment]
  name varchar(50) [not null, unique]
}

Table payment_types {
  id int [pk, increment]
  name varchar(50) [not null, unique]
}

Table requests {
  id int [pk, increment]
  user_id int [not null, ref: > users.id]
  service_id int [not null, ref: > services.id]
  status_id int [not null, default: 1, ref: > statuses.id]
  payment_type_id int [not null, ref: > payment_types.id]
  address varchar(255) [not null]
  contact_phone varchar(20) [not null]
  service_date date [not null]
  service_time time [not null]
  cancel_reason text [null]
  created_at datetime [not null, default: `now()`]
}
```

`ref: > users.id` означает «многие к одному»: много заявок ссылаются на одного пользователя. Экспорт — кнопка Export → PNG или PDF.

**Что должно быть на хорошей диаграмме:** все таблицы; у каждой — все поля с типами; отмечены первичные ключи; линии связей идут от FK к PK, видна кратность (1 — ко многим); ничего не налезает друг на друга; подпись с названием базы. Сохраните PNG и PDF — один из этих форматов подойдёт под требования любого варианта.

**Типичные ошибки:**

1. Сдан дамп, который ни разу не разворачивали, — а в нём нет данных (сняли галочку) или нет `DROP TABLE`, и повторный импорт падает.
2. Дамп сохранён в `.zip`/`.gz` без нужды, или кодировка выгрузки не UTF-8.
3. Диаграмма из ЛР3 сдаётся как диаграмма по факту, хотя таблицы с тех пор поменялись.
4. На скриншоте Дизайнера таблицы свалены в кучу, линии не видны.
5. Дамп кладут в репозиторий вместе с паролями от реального хостинга (здесь их нет, но привычку заведите сейчас: в репозиторий — только учебные данные).

**Связь с экзаменом.** Дамп `.sql` и диаграмма — это то, что вы физически сдаёте по базе данных. Совет на экзамене: делайте быстрый экспорт после каждого крупного шага (создана структура, добавлены данные, закончена админка) и называйте файлы с номером: `portal_01_structure.sql`, `portal_02_data.sql`. Это три клика и 10 секунд, а спасти могут весь экзамен.

## Задание

**Цель:** получить проверенный дамп базы своего портала и диаграмму БД двумя способами.

**Исходные данные:** база вашего портала после ЛР18–19 (структура, справочники, 11 пользователей, 20+ заявок); описание DBML учебной базы из лекции как образец.

**Ход работы:**

1. Посчитайте строки во всех таблицах своей базы запросом `UNION ALL` из лекции, запишите результат.
2. Сделайте быстрый экспорт базы. Откройте файл в VS Code, найдите и отметьте комментариями (в отчёте): `CREATE TABLE requests`, первый `INSERT INTO users`, блок внешних ключей.
3. Сделайте «чистовой» экспорт обычным способом с `DROP TABLE` и многострочными `INSERT`. Назовите файл `db/portal_<фамилия>.sql`.
4. Сделайте отдельный экспорт **только структуры** (снимите «Данные») — `db/portal_<фамилия>_structure.sql`.
5. Проверьте дамп: создайте `portal_check`, импортируйте туда `db/portal_<фамилия>.sql`, сравните число строк с шагом 1, проверьте кириллицу и связи.
6. Проверьте устойчивость: импортируйте тот же дамп в `portal_check` второй раз. Ошибок быть не должно (за это отвечает `DROP TABLE`).
7. Откройте «Дизайнер» своей базы, расставьте таблицы, сохраните диаграмму экспортом схемы (PDF/SVG) или скриншотом — `db/diagram_designer.png` (или `.pdf`).
8. Опишите свою базу на DBML (по образцу из лекции), постройте диаграмму на dbdiagram.io, экспортируйте в PNG — `db/diagram_dbml.png`, текст сохраните в `db/schema.dbml`.
9. Сравните диаграмму с ER-диаграммой из ЛР3: выпишите 2–3 отличия (что добавилось или изменилось и почему).
10. Удалите базу `portal_check`. Закоммитьте все файлы из `db/`.

**Что сдать:** `db/portal_<фамилия>.sql`, `db/portal_<фамилия>_structure.sql`, `db/diagram_designer.png` (или PDF/SVG), `db/diagram_dbml.png`, `db/schema.dbml`, короткий отчёт с числом строк (шаг 1 и шаг 5) и отличиями от ER-диаграммы.

## Критерии оценки

| Аспект | 2 балла | 1 балл | 0 баллов |
|---|---|---|---|
| Полный дамп | структура + данные, `DROP TABLE`, UTF-8, разворачивается дважды без ошибок | разворачивается, но с ручными правками | не разворачивается или нет данных |
| Проверка дампа | число строк сверено, кириллица и связи проверены | сверено частично | проверки нет |
| Диаграмма Дизайнера | все таблицы, поля и связи видны, ничего не перекрывается | есть, но плохо читается | отсутствует |
| Диаграмма DBML | `schema.dbml` соответствует реальной базе, PNG экспортирован | расхождения в 1–2 полях | отсутствует |
| Анализ отличий от ЛР3 | отличия указаны и объяснены | только перечислены | нет |

## Если не успел / для сильных

**Минимум для зачёта:** полный дамп, развёрнутый в `portal_check` без ошибок, и скриншот Дизайнера.
**Усложнение:** напишите `.bat`-файл (или скрипт для терминала VS Code), который одной командой делает дамп через `mysqldump` с датой и временем в имени файла, и проверьте восстановление из него через `mysql -u root < файл.sql`.
