## Лекция

**Зачем думать о данных до кода.** Портал заявок, по сути, — красивая оболочка вокруг базы данных. Регистрация *записывает* пользователя, вход *ищет* его, «мои заявки» *выбирают* заявки по пользователю, админка *меняет* статус. Если база спроектирована криво, криво будет всё: лишние поля, дубли, запросы на полэкрана. В задании 3 экзамена прямо требуется **диаграмма базы данных**, а задание 1 без базы просто не работает. Поэтому сегодня учимся видеть в ТЗ не текст, а *данные*.

**Сущность.** Сущность — класс объектов, о которых системе нужно хранить информацию. Признаки: у неё много экземпляров, и каждый можно отличить от другого. В базе сущность станет **таблицей**, экземпляр — **строкой**.

Как найти сущности в ТЗ: выписать существительные и отсеять лишние.

> «*Клиент* регистрируется, оформляет *заявку* на *услугу*, выбирает *тип оплаты*. *Администратор* меняет *статус* заявки и указывает *причину отмены*».

- **Клиент**, **Администратор** — оба входят в систему по логину и паролю. Делать две таблицы не нужно: это одна сущность **Пользователь** с атрибутом «роль».
- **Заявка** — главная сущность системы.
- **Услуга** — список из ТЗ (общая уборка, генеральная…). Это сущность-**справочник**.
- **Тип оплаты** (наличные, карта) — тоже справочник, маленький.
- **Статус** (новая, в работе, выполнено, отменено) — справочник.
- **Причина отмены** — не сущность. Это текст, который относится к одной конкретной заявке, значит, это **атрибут** заявки.

Проверочный вопрос: «Нужно ли хранить у этого объекта несколько своих свойств или их много штук?» Если у «причины отмены» нет своих свойств и она принадлежит одной заявке, это атрибут.

**Атрибут.** Свойство сущности, будущий **столбец** таблицы. У каждого атрибута есть тип (текст, число, дата) и ограничения (обязательный, уникальный, формат).

| Сущность | Атрибуты |
|---|---|
| Пользователь | id, логин (уникальный), пароль (хеш), ФИО, телефон, email, роль |
| Заявка | id, пользователь, адрес, телефон, дата и время, услуга, иная услуга (текст), тип оплаты, статус, причина отмены, дата создания |
| Услуга | id, название |
| Статус | id, название |
| Тип оплаты | id, название |

Обратите внимание:

- **id** — у каждой сущности есть идентификатор, который никогда не меняется. Логин или email на эту роль не годятся: человек может захотеть их поменять. Подробнее о ключах — в ПР4.
- **Пароль** храним не сам, а его *хеш* (в PHP это `password_hash`, модуль 5). Поэтому в атрибуте пишем «хеш пароля».
- **Атомарность:** ФИО можно хранить одним полем (как требует форма) или тремя (фамилия, имя, отчество). Оба варианта допустимы. Главное — не складывать в одно поле «телефон и email через запятую».
- **Производные данные не храним.** «Количество заявок пользователя» не нужно отдельным полем, его можно посчитать запросом.

**Связи.** Связь показывает, как экземпляры сущностей относятся друг к другу. Мощность (кардинальность) связи бывает трёх видов.

**1:1 (один к одному).** Одному экземпляру A соответствует не больше одного B, и наоборот. Пример: *Пользователь — Паспортные данные*, *Заявка — Отзыв* (на одну заявку можно оставить один отзыв). На практике 1:1 встречается редко: обычно такие данные просто кладут в ту же таблицу. Отдельная таблица оправдана, если данные необязательные, большие или секретные.

**1:N (один ко многим).** Самая частая связь. Один пользователь создаёт много заявок, но у каждой заявки ровно один автор. Один статус — у многих заявок, у заявки один текущий статус.

```
Пользователь 1 ──────< N Заявка
Статус       1 ──────< N Заявка
Услуга       1 ──────< N Заявка
Тип оплаты   1 ──────< N Заявка
```

Правило реализации: **внешний ключ ставится на стороне «много»**. В заявке появляется поле `user_id`, а не в пользователе поле «список заявок». В ячейке таблицы должно быть одно значение, а не список.

**M:N (многие ко многим).** Каждому A соответствует много B, и каждому B — много A. Пример: если в варианте можно выбрать **несколько** услуг в одной заявке (уборка + химчистка ковра), то одна заявка содержит много услуг, а одна услуга входит во многие заявки. Ещё примеры: *Студент — Курс* (вариант «запись на курсы»), *Блюдо — Заказ* (вариант «кафе»).

Напрямую M:N в реляционной базе не хранится. Её разбивают на две связи 1:N через **ассоциативную (связующую) таблицу**:

```
Заявка 1 ──< N  Заявка_Услуга  N >── 1 Услуга
                (order_id, service_id, количество, цена)
```

Связующая таблица может иметь свои атрибуты: количество, цену на момент заказа. Это частый вопрос на собеседованиях и сильный ход в вариативной части экзамена.

**Обязательность.** Помимо «один или много» указывают, *может ли связи не быть*. Заявка **обязательно** имеет автора, а пользователь **может** не иметь ни одной заявки (только зарегистрировался). Это влияет на ограничения: `user_id` в заявке не может быть пустым (`NOT NULL`).

**Нотации.** Связи рисуют по-разному. Две популярные:

- **Нотация Чена** (учебная): сущность — прямоугольник, атрибут — овал, связь — ромб. Наглядно, но громоздко.
- **«Вороньи лапки» (Crow's Foot, IE)**: сущность — прямоугольник со списком атрибутов, связь — линия с концами: `|` — один, `<` (лапка) — много, `o` — может не быть. Так рисуют draw.io, phpMyAdmin Designer, dbdiagram и MySQL Workbench. Её и используем в курсе.

```
┌─────────────┐            ┌──────────────┐
│ users       │            │ orders       │
├─────────────┤            ├──────────────┤
│ PK id       │ ||──────o< │ PK id        │
│ login       │            │ FK user_id   │
│ ...         │            │ ...          │
└─────────────┘            └──────────────┘
 «один и только один» пользователь — «ноль или много» заявок
```

**Модели разного уровня.**

1. **Концептуальная** — сущности и связи, без типов. Её можно обсуждать с заказчиком.
2. **Логическая** — плюс атрибуты, ключи, связи раскрыты (M:N → связующая таблица).
3. **Физическая** — под конкретную СУБД: типы `INT`, `VARCHAR(100)`, `DATETIME`, индексы. Её сделаем в ЛР3 и модуле 4.

**Типичные ошибки:**

- Отдельные таблицы `clients` и `admins` с одинаковыми полями. Правильно — одна `users` с ролью.
- Статус хранится текстом в каждой заявке («Новая», «новая», «Новая ») — опечатки ломают фильтр. Справочник это решает.
- Список в ячейке: `services = "1,3,4"`. Это нарушение 1НФ (ПР4) и признак пропущенной M:N.
- Внешний ключ не на той стороне: в `users` поле `order_id`. Тогда у пользователя может быть только одна заявка.
- Причину отмены вынесли в отдельную таблицу без причины: лишний JOIN без пользы.
- Сущность «Сайт» или «Админ-панель». Это части интерфейса, а не данные.

**Связь с экзаменом.** В задании 3 по образцу требуется диаграмма БД, и эксперт смотрит, соответствует ли она ТЗ: есть ли все поля формы, связаны ли таблицы, отмечены ли ключи. Кроме того, правильная модель экономит время в задании 1: запросы «заявки пользователя» и «все заявки с ФИО» пишутся в одну строку.

## Задание

**Цель:** научиться выделять из ТЗ сущности, атрибуты и связи и правильно определять тип связи.

**Исходные данные:** ТЗ «Мой Не Сам» (ПР1), ТЗ-2 «Починим» (ПР1) и шесть пар ниже.

**Ход работы:**

2. (15 мин) **Определите тип связи** (1:1, 1:N, M:N) и обязательность для пар:
   - Пользователь — Заявка;
   - Заявка — Отзыв (один отзыв на заявку);
   - Студент — Курс (вариант «запись на курсы»);
   - Столик — Бронь (вариант «кафе»);
   - Заказ — Блюдо;
   - Сотрудник — Пропуск в офис.
   Для каждой M:N назовите связующую таблицу и её атрибуты.
3. (25 мин) **Модель для ТЗ-2 «Починим».** Выпишите сущности (не меньше 5) и атрибуты каждой с пометкой «обязательный/уникальный». Нарисуйте концептуальную схему на бумаге в нотации «вороньи лапки».
4. (15 мин) **Расширение.** Заказчик говорит: «В одной заявке клиент может сдать несколько устройств, у каждого своя неисправность и своя стоимость». Как изменится модель? Перерисуйте нужную часть.
5. (15 мин) **Найди ошибки.** Разберите модель ниже, найдите не меньше 4 ошибок и предложите исправление:

```

admins(id, login, password)
orders(id, client_login, services, status, cancel_reason_id, total)
```

6. (10 мин) Обсуждение в группе: сравните свои модели ТЗ-2 с соседом, договоритесь об одном варианте.

**Что сдать:** лист с ответами по пунктам 1, 2, 5; концептуальную схему ТЗ-2 (п. 3) и её изменённую часть (п. 4).
