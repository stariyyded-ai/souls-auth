## Лекция

**Почему таблица Excel — плохая база данных.** Представьте, что администратор «Мой Не Сам» ведёт заявки в одной таблице Excel:

| Заявка | Логин | ФИО | Телефон клиента | Услуги | Статус | Оплата |
|---|---|---|---|---|---|---|
| 101 | ivanov | Иванов Иван Иванович | +7(900)-111-22-33 | Общая уборка, Химчистка ковров | Новая | Карта |
| 102 | ivanov | Иванов И. И. | +7(900)-111-22-33 | Генеральная уборка | в работе | Наличные |
| 103 | petrova | Петрова Анна Сергеевна | +7(901)-222-33-44 | Общая уборка | Выполнено | карта |

Проблемы видны сразу:

- **Аномалия обновления.** Иванов сменил телефон, его надо исправить во всех строках. Пропустили одну, и данные противоречат друг другу. ФИО уже записано по-разному.
- **Аномалия вставки.** Нельзя добавить новую услугу «Мойка окон» в каталог, пока на неё нет ни одной заявки.
- **Аномалия удаления.** Удалили единственную заявку Петровой — пропали все данные о ней как о клиенте.
- **Мусор в значениях.** «в работе» и «В работе», «Карта» и «карта» — для фильтра это разные статусы.
- **Список в ячейке.** «Общая уборка, Химчистка ковров» — как посчитать, сколько раз заказывали химчистку?

**Нормализация** — пошаговое разбиение таблиц так, чтобы каждый факт хранился **ровно в одном месте**. Для практики хватает трёх нормальных форм. Каждая следующая включает предыдущую.

**Сначала о ключах: без них нормализацию не объяснить.**

- **Первичный ключ (PK, primary key)** — столбец (или набор столбцов), значение которого уникально и однозначно определяет строку. Не может быть `NULL` и не должен меняться. Обычно это **суррогатный** ключ `id INT AUTO_INCREMENT` — число без смысла, которое выдаёт база.
- **Естественный ключ** — уникальное значение из жизни: логин, email, номер паспорта. Его делаем `UNIQUE`, но PK оставляем `id`, потому что естественные значения иногда меняются.
- **Составной ключ** — PK из нескольких столбцов, например `(order_id, service_id)` в связующей таблице.
- **Внешний ключ (FK, foreign key)** — столбец, значение которого должно совпадать с PK другой таблицы. `orders.user_id` → `users.id`. Это «ссылка» между таблицами.

**1НФ: атомарность.** Таблица в 1НФ, если в каждой ячейке одно значение (никаких списков) и нет повторяющихся групп столбцов (`услуга1`, `услуга2`, `услуга3`). Есть первичный ключ.

Решение для нашей таблицы: одна строка — одна пара «заявка — услуга».

| order_id | service | login | fio | … |
|---|---|---|---|---|
| 101 | Общая уборка | ivanov | Иванов Иван Иванович | … |
| 101 | Химчистка ковров | ivanov | Иванов Иван Иванович | … |
| 102 | Генеральная уборка | ivanov | … | … |

Теперь ключ составной — `(order_id, service)`. Списков нет, но дублей стало ещё больше. Идём дальше.

**2НФ: всё зависит от всего ключа.** Таблица в 2НФ, если она в 1НФ и каждый неключевой столбец зависит от **всего** составного ключа, а не от его части. Проверяем: статус и оплата зависят только от `order_id` (у заявки один статус, сколько бы в ней ни было услуг). ФИО тоже не зависит от услуги. Это **частичные зависимости**, их выносим:

```
orders(order_id PK, login, fio, phone, status, payment)
order_services(order_id FK, service, PK(order_id, service))
```

Если PK простой (один столбец `id`), таблица в 1НФ автоматически в 2НФ: частичной зависимости от «части» одного столбца быть не может.

**3НФ: никаких зависимостей через посредника.** Таблица в 3НФ, если она в 2НФ и неключевые столбцы зависят **только от ключа**, а не друг от друга (нет **транзитивных** зависимостей). В `orders` ФИО и телефон зависят от логина, а логин — от заявки: `order_id → login → fio`. Это транзитивная зависимость, данные клиента выносим в `users`. Тексты статусов, оплат и услуг повторяются — выносим в справочники.

Итог — та самая модель из ЛР3:

```
users(id PK, login UNIQUE, password, fio, phone, email, role_id FK)
orders(id PK, user_id FK, address, phone, service_datetime,
       payment_type_id FK, status_id FK, cancel_reason, created_at)
order_services(order_id FK, service_id FK, PK(order_id, service_id))  -- если услуг несколько
services(id PK, name UNIQUE)
statuses(id PK, name UNIQUE)
payment_types(id PK, name UNIQUE)
```

Короткая формула для запоминания (классическая): неключевой атрибут должен зависеть «от ключа (1НФ), от всего ключа (2НФ) и ни от чего, кроме ключа (3НФ)».

**А телефон в заявке — это не дубль?** В ТЗ у заявки есть свой «контактный телефон»: клиент может указать номер родственника, который будет дома. Это **другой факт**, а не копия телефона из профиля, поэтому поле `orders.phone` 3НФ не нарушает. Нормализация — не механическое «убрать все одинаковые слова», а вопрос «от чего зависит этот факт?».

**Ссылочная целостность.** Это правило: внешний ключ не может указывать на несуществующую строку. Если в `orders` есть `user_id = 15`, пользователь с `id = 15` обязан существовать. В MySQL/MariaDB это обеспечивает ограничение `FOREIGN KEY`. Работает оно только с движком таблиц **InnoDB** (он по умолчанию в современных версиях; старый MyISAM внешние ключи игнорирует).

```sql
CREATE TABLE orders (
  id INT AUTO_INCREMENT PRIMARY KEY,
  user_id INT NOT NULL,
  status_id INT NOT NULL DEFAULT 1,
  -- ...
  FOREIGN KEY (user_id)   REFERENCES users(id)    ON DELETE CASCADE,
  FOREIGN KEY (status_id) REFERENCES statuses(id) ON DELETE RESTRICT
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

Что делать с заявками, если удаляют «родителя»? Это задаётся правилами `ON DELETE` / `ON UPDATE`:

| Правило | Что происходит | Когда уместно |
|---|---|---|
| `RESTRICT` / `NO ACTION` | Удаление родителя запрещено, пока есть ссылки (поведение по умолчанию) | Статус, услуга: нельзя удалить «В работе», если есть такие заявки |
| `CASCADE` | Вместе с родителем удаляются все дочерние строки | Удалили пользователя — удалили его заявки (осторожно!) |
| `SET NULL` | В дочерних строках FK становится `NULL` (столбец должен допускать NULL) | Удалили услугу из каталога — заявки остались, услуга «не указана» |

Что вы увидите на практике: попытка вставить заявку с `status_id = 99` даст ошибку `#1452 - Cannot add or update a child row: a foreign key constraint fails`. Это не баг, база защищает данные. Порядок заполнения: сначала справочники и пользователи, потом заявки.

**Когда нормализация мешает.** Иногда сознательно оставляют «лишние» данные (денормализация), например цену услуги на момент заказа в `order_services.price`, чтобы при подорожании старые заявки не изменились. Это не ошибка, если решение осознанное. Для экзамена ориентир простой: 3НФ плюс справочники для всего, что выбирается из списка.

**Типичные ошибки:**

- PK — логин или email. Пользователь сменил email, и поехали все ссылки.
- FK есть «по смыслу» (столбец `user_id`), но ограничение `FOREIGN KEY` не создано: база не защищает данные.
- Таблицы MyISAM, внешние ключи «создались», но не работают.
- Типы FK и PK не совпадают (`INT` и `VARCHAR`) — MySQL не даст создать связь.
- `ON DELETE CASCADE` поставлен на справочник статусов: удалили статус — исчезли все заявки с ним.
- «Перенормализовали»: ФИО разбили на три таблицы, а адрес — на шесть. Для портала заявок это лишнее.

**Связь с экзаменом.** Критерий «безопасность ИС» касается и данных: целостность, отсутствие противоречий, корректные связи. Диаграмма в задании 3 должна показывать PK и FK. А правильно нормализованная база делает запрос админки «все заявки с ФИО клиента и названием статуса» простым JOIN-ом (модуль 4).

## Критерии оценки

| Аспект | 2 балла | 1 балл | 0 баллов |
|---|---|---|---|
| Аномалии | Три верных примера (обновление, вставка, удаление) | 1–2 примера | Нет |
| 1НФ и 2НФ | Списки разбиты, ключ указан, частичные зависимости вынесены | Один шаг с ошибкой | Шаги не выполнены |
| 3НФ | Клиенты, столики (залы), статусы, блюда в отдельных таблицах, связь M:N бронь—блюда через связующую таблицу | 1 транзитивная зависимость осталась | Модель не в 3НФ |
| Ключи и целостность | PK/FK/UNIQUE верны, правила ON DELETE обоснованы | Без обоснования или 1 ошибка | Не выполнено |
| SQL | Два корректных `CREATE TABLE` с FK, InnoDB, utf8mb4 | Синтаксические ошибки или нет FK | Нет |
