## Лекция

**От рисунка на бумаге к рабочей схеме.** На ПР3 вы набросали модель на бумаге. Сегодня делаем из неё **ER-диаграмму** (Entity–Relationship, «сущность–связь») уровня, по которому завтра можно создать базу в phpMyAdmin, не думая. Такая диаграмма — артефакт задания 3 экзамена, и она же становится частью проектной документации в ЛР4. Хорошая ER-диаграмма похожа на план квартиры для ремонтников: по ней видно, где какие комнаты и как они соединены, и никто не вешает дверь в стену.

**Что должно быть на ER-диаграмме физического уровня.**

1. **Таблицы** с именами латиницей во множественном числе или в одном стиле: `users`, `orders`, `services`. Не смешивайте `Users`, `order`, `tbl_Service`.
2. **Столбцы** с типами данных MySQL.
3. **Первичный ключ (PK)** в каждой таблице, обычно `id` с автоинкрементом.
4. **Внешние ключи (FK)** с явной пометкой, на какую таблицу они ссылаются.
5. **Связи** линиями с правильными концами (нотация «вороньи лапки»), от FK к PK.
6. Желательно: пометки `NOT NULL`, `UNIQUE`, `DEFAULT`.

**Типы данных MySQL/MariaDB, которых хватит для портала.**

| Тип | Для чего | Пример |
|---|---|---|
| `INT` (+ `AUTO_INCREMENT`) | id, ключи, количество | `id INT AUTO_INCREMENT PRIMARY KEY` |
| `VARCHAR(n)` | короткие строки до n символов | логин, ФИО, телефон, email |
| `TEXT` | длинный текст | описание, причина отмены |
| `DATE`, `TIME`, `DATETIME` | дата, время, дата и время | желаемая дата услуги |
| `DECIMAL(10,2)` | деньги (точно, без округлений) | стоимость |
| `TINYINT(1)` / `BOOLEAN` | да/нет | флаг «иная услуга» |
| `TIMESTAMP` / `DATETIME DEFAULT CURRENT_TIMESTAMP` | когда создана запись | `created_at` |

Важные мелочи:

- **Пароль** храним хешем от `password_hash()`. Сейчас хеш занимает 60 символов (bcrypt), но документация PHP рекомендует поле `VARCHAR(255)` на будущее. Делаем `password VARCHAR(255)`.
- **Телефон** — строка, а не число: в нём `+`, скобки и дефисы, а ведущие нули не должны пропадать. Формат `+7(XXX)-XXX-XX-XX` занимает ровно 17 символов, берём `VARCHAR(20)`.
- **Деньги** — `DECIMAL`, а не `FLOAT`: у `FLOAT` бывают ошибки округления.
- **Кодировка** базы — `utf8mb4` (полноценный UTF-8, включая эмодзи). Это задаётся при создании базы в модуле 4, но на диаграмме можно подписать.

**Эталонная физическая модель «Мой Не Сам».** Используйте её как образец, а свою делайте по варианту.

```
roles            (id PK, name VARCHAR(20) UNIQUE)                  -- 'user', 'admin'
users            (id PK, login VARCHAR(50) UNIQUE NOT NULL,
                  password VARCHAR(255) NOT NULL,
                  fio VARCHAR(150) NOT NULL, phone VARCHAR(20) NOT NULL,
                  email VARCHAR(100) NOT NULL,
                  role_id INT NOT NULL FK → roles.id DEFAULT 1)
services         (id PK, name VARCHAR(100) UNIQUE)                 -- 4 услуги из ТЗ
payment_types    (id PK, name VARCHAR(50) UNIQUE)                  -- наличные, карта
statuses         (id PK, name VARCHAR(50) UNIQUE)                  -- новая, в работе, выполнено, отменено
orders           (id PK,
                  user_id INT NOT NULL FK → users.id,
                  address VARCHAR(255) NOT NULL,
                  phone VARCHAR(20) NOT NULL,
                  service_datetime DATETIME NOT NULL,
                  service_id INT NULL FK → services.id,   -- NULL, если выбрана «иная услуга»
                  other_service TEXT NULL,
                  payment_type_id INT NOT NULL FK → payment_types.id,
                  status_id INT NOT NULL FK → statuses.id DEFAULT 1,
                  cancel_reason TEXT NULL,
                  created_at DATETIME DEFAULT CURRENT_TIMESTAMP)
```

Связи: `roles 1—N users`, `users 1—N orders`, `services 1—N orders` (необязательная со стороны заявки), `payment_types 1—N orders`, `statuses 1—N orders`.

Почему роль сделана справочником, а не полем `is_admin`? Оба варианта рабочие. Справочник легко расширить (например, ролью «мастер»). Вариант попроще — `role VARCHAR(10) DEFAULT 'user'` — тоже допустим на экзамене, если вы последовательны.

Почему **`service_id` может быть NULL**? По ТЗ клиент выбирает услугу из списка *или* описывает иную. Значит, у заявки либо заполнен `service_id`, либо `other_service`. Такие правила «одно из двух» проверяются в PHP при сохранении формы.

**draw.io: как рисовать быстро.** draw.io работает в браузере (app.diagrams.net) и как десктоп-приложение, бесплатно и без регистрации. Файлы сохраняются в формате `.drawio`; экспорт — в PNG, SVG, PDF.

1. **Создать диаграмму:** *Create New Diagram* → шаблон *Blank* (или раздел шаблонов *Software*, если хотите посмотреть пример).
2. **Включить библиотеку:** слева внизу *+ More Shapes* → поставить галочку **Entity Relation** → *Apply*. Появятся фигуры *Table*, *Attribute*, *Relation* и концы связей.
3. **Таблица:** перетащите фигуру *Table* (заголовок + строки). Двойной щелчок по строке — редактирование. Новая строка: выделите существующую строку и нажмите Ctrl+Enter (дублировать), затем переименуйте. Удобный формат строки: `PK | id INT` или просто `id INT PK`.
4. **Связь:** наведите на строку FK и тяните коннектор к строке PK в другой таблице. Затем на правой панели *Arrange/Style* выберите концы линии: **Line start / Line end** → `ERmandOne` (две черты, «ровно один»), `ERmany` / `ERzeroToMany` / `ERoneToMany` («вороньи лапки»). Через *Edit Style* можно задать вручную:

```
edgeStyle=entityRelationEdgeStyle;endArrow=ERzeroToMany;startArrow=ERmandOne;
```

5. **Быстрый способ из SQL.** В draw.io есть вставка таблиц из текста SQL: меню *Arrange → Insert → Advanced → SQL* (*Упорядочить → Вставить → Дополнительно → SQL*; путь может немного отличаться в разных версиях). Вставьте `CREATE TABLE` — draw.io нарисует таблицы, связи останется провести самим. Это пригодится на экзамене, когда база уже создана, а диаграмму нужно сдать.
6. **Оформление:** выровняйте таблицы (справочники вокруг `orders`), чтобы линии не пересекались; подпишите заголовок диаграммы; включите *View → Grid*, чтобы держать ровную сетку.
7. **Экспорт:** *File → Export as → PNG*, масштаб 200 %, галочка *Include a copy of my diagram* (тогда PNG можно снова открыть в draw.io и редактировать).

**Альтернативы.** phpMyAdmin умеет строить схему готовой базы (вкладка *Дизайнер*/*Designer*), а в dbdiagram.io схему описывают текстом. Это пригодится в модуле 4 (ЛР20). Но draw.io не зависит от готовой базы, им можно проектировать заранее.

**Типичные ошибки:**

- Линия соединяет таблицы «где-то сбоку», а не FK с PK. Непонятно, по какому полю связь.
- Концы связей перепутаны: «лапка» у `users`, а не у `orders`. Читается как «у заявки много пользователей».
- Нет типов данных или везде `VARCHAR(255)`, включая даты и id.
- Телефон как `INT` — `+7(` в число не поместится.
- В `orders` есть поле `status VARCHAR`, и одновременно есть таблица `statuses`, которая ни с чем не связана.
- Диаграмма не совпадает с формами из ТЗ: на форме есть «тип оплаты», а в базе нет. Эксперт сверяет именно это.
- Отправили `.drawio` без PNG, а у проверяющего нет draw.io. Всегда экспортируйте картинку.

**Проверка диаграммы за 2 минуты (чек-лист):** каждое поле каждой формы ТЗ есть в какой-то таблице; у каждой таблицы есть PK; у каждой линии есть FK; лапка у таблицы на стороне «много»; справочники заполнены значениями из ТЗ (можно подписать рядом); нет таблиц без связей.

## Задание

**Цель:** построить ER-диаграмму физического уровня для своего варианта портала заявок.

**Исходные данные:** ваш вариант проекта; разбор ТЗ (ПР1); модель данных (ПР3); эталон «Мой Не Сам» из лекции. Если вариант пока не выдан, используйте ТЗ-2 «Починим».

**Ход работы:**

1. (10 мин) Выпишите все поля всех форм своего варианта (регистрация, заявка, админ-панель) — это контрольный список для диаграммы.
2. (10 мин) Повторите эталон: откройте draw.io, подключите библиотеку *Entity Relation*, нарисуйте таблицы `users` и `orders` из лекции и одну связь между ними с правильными концами. Покажите преподавателю.
3. (35 мин) Нарисуйте полную диаграмму своего варианта: все таблицы, столбцы с типами, PK, FK, `NOT NULL`/`UNIQUE`/`DEFAULT` где нужно; связи с концами «вороньи лапки».
4. (5 мин) Рядом со справочниками подпишите их значения из ТЗ (например: «statuses: Новая, В работе, Выполнено, Отменено»).
5. (10 мин) Пройдите чек-лист из лекции. Отметьте галочками в контрольном списке п. 1, где хранится каждое поле формы.
6. (5 мин) Попробуйте вставку через *Arrange → Insert → Advanced → SQL*: вставьте `CREATE TABLE statuses (id INT PRIMARY KEY, name VARCHAR(50));` и посмотрите результат (удалите после проверки).
7. (5 мин) Экспортируйте PNG (200 %, с копией диаграммы) и сохраните `er.drawio` и `er.png` в папку `portal/docs/`.
8. (5 мин) Закоммитьте: `git add docs/` → `git commit -m "ER-диаграмма портала"` → `git push`.

**Что сдать:** `docs/er.drawio` и `docs/er.png` в репозитории; контрольный список полей форм с отметками (можно в `docs/requirements.md`).

## Критерии оценки

| Аспект | 2 балла | 1 балл | 0 баллов |
|---|---|---|---|
| Соответствие ТЗ | Все поля всех форм варианта есть в таблицах | Не хватает 1–2 полей | Не хватает более 2 полей или таблиц |
| Ключи | PK во всех таблицах, все FK отмечены и связаны | 1 ошибка (нет FK или PK) | Ключи не указаны |
| Связи | Все связи от FK к PK, концы «вороньи лапки» верны | 1–2 перепутанных конца | Связей нет или они случайные |
| Типы данных | Типы подходят (телефон строкой, пароль 255, даты DATE/DATETIME) | 1–2 неудачных типа | Типов нет |
| Оформление и сдача | Аккуратно, без пересечений, PNG + .drawio в Git | Сдано, но читается с трудом или нет одного файла | Не сдано |

## Если не успел / для сильных

**Минимум для зачёта:** диаграмма с таблицами `users`, `orders`, `statuses`, PK/FK и тремя правильными связями, экспортированная в PNG.
**Усложнение:** напишите по своей диаграмме скрипт `docs/schema.sql` с `CREATE TABLE` и внешними ключами (InnoDB, utf8mb4) и проверьте его импортом в phpMyAdmin в тестовую базу.

:::quiz
? Почему телефон хранят в `VARCHAR`, а не в `INT`?
- [ ] `INT` занимает слишком много места на диске
- [ ] В `VARCHAR` поиск по базе работает быстрее
- [ ] `INT` нельзя сделать `NOT NULL`
- [x] В номере есть `+`, скобки и дефисы, а с числом ничего не считают
> Номер вида `+7(900)-111-22-33` — строка. Складывать телефоны не нужно, а формат надо сохранить посимвольно.

? Зачем для пароля поле `VARCHAR(255)`, а не `VARCHAR(20)`?
- [x] Хранится не пароль, а его хеш, который длиннее и может вырасти
- [ ] Чтобы пользователи могли придумывать пароли до 255 символов
- [ ] Так требует draw.io при рисовании диаграммы
- [ ] Короткие поля нельзя делать `NOT NULL`
> `password_hash()` даёт хеш длиной 60 символов, а документация PHP советует 255 с запасом на будущее.

? Почему в эталонной модели `service_id` в заявке может быть `NULL`?
- [ ] Администратор выбирает услугу позже, после заявки
- [x] Клиент выбирает услугу из списка или описывает «иную услугу» текстом
- [ ] `NULL` нужен, чтобы заявку можно было удалить
- [ ] Внешние ключи всегда должны допускать `NULL`
> У заявки заполнен либо `service_id`, либо `other_service`. Правило «одно из двух» проверяют в PHP при сохранении.

? Как быстро проверить, что ER-диаграмма соответствует ТЗ?
- [ ] Убедиться, что все поля имеют тип `VARCHAR(255)`
- [ ] Посчитать, что таблиц ровно пять
- [x] Проверить, что каждое поле форм есть в таблице, у таблиц есть PK, у линий — FK
- [ ] Экспортировать её в PNG и посмотреть на размер файла
> Чек-лист на 2 минуты: поля форм из ТЗ, PK у каждой таблицы, FK у каждой связи, справочники со значениями из ТЗ.
:::
