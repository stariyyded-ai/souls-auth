## Лекция

**Знакомая ситуация.** Файлы `diplom_final.docx`, `diplom_final2.docx`, `diplom_final_ТОЧНО_ПОСЛЕДНИЙ.docx`. С кодом так же, только хуже: вчера форма регистрации работала, сегодня вы «чуть-чуть поправили», и всё сломалось, а что именно меняли, не помните. Git решает эту проблему. Это **система контроля версий**: она хранит историю изменений проекта, позволяет вернуться к любому сохранённому состоянию, попробовать идею в отдельной ветке и выложить код на GitHub, чтобы он не пропал вместе с флешкой.

В нашем курсе Git — страховочный трос для сквозного проекта: портал вы будете строить почти весь год. Отдельным критерием в плане экзамена Git не указан, но умение пользоваться им ждут от любого джуна на собеседовании, а на практике он не раз спасёт ваш проект.

**Три зоны Git.** Это главное, что надо понять, остальное — команды.

```
 Рабочая папка         Индекс (staging)         Репозиторий (.git)
 (ваши файлы)    ──git add──►  (что войдёт   ──git commit──►  (история
  изменили файл              в снимок)                         снимков)
```

- **Рабочая папка** — обычные файлы, которые вы правите в VS Code.
- **Индекс** — «корзина» перед кассой: вы выбираете, какие изменения войдут в следующий снимок.
- **Коммит** — сам снимок проекта с подписью: кто, когда и зачем изменил. Коммиты выстраиваются в цепочку, это и есть история.

**Первая настройка (один раз на компьютере):**

```bash
git --version                                  # проверить, что Git установлен
git config --global user.name "Иван Петров"
git config --global user.email "ivan@example.com"
git config --global init.defaultBranch main    # основная ветка будет называться main
```

На компьютере колледжа добавлять `--global` можно только на своей учётной записи. Если ПК общий, задайте имя без `--global`, внутри папки проекта: тогда оно будет действовать только для этого репозитория.

**Базовый цикл: init → add → commit.**

```bash
cd C:/xampp/htdocs/portal
git init                       # создать репозиторий (появится скрытая папка .git)
git status                     # что изменено, что в индексе
git add index.php css/style.css   # добавить конкретные файлы
git add .                      # или все изменения в текущей папке
git commit -m "Каркас портала: главная, стили, структура папок"
git log --oneline              # короткая история
```

`git status` — самая частая команда. Запускайте её перед каждым `add` и `commit`: она показывает красным неотслеживаемые и изменённые файлы, зелёным — то, что уже в индексе.

**Как писать сообщения коммитов.** Коммит — запись в журнале, читать её будете вы сами через месяц. Плохо: `"fix"`, `"123"`, `"изменения"`. Хорошо: `"Форма регистрации: проверка длины логина"`, `"ER-диаграмма: добавлена таблица статусов"`. Правило: одно логическое изменение — один коммит; сообщение отвечает на вопрос «что сделал этот коммит?».

**.gitignore — что НЕ кладём в репозиторий.** Файл `.gitignore` в корне проекта перечисляет файлы, которые Git не отслеживает:

```gitignore
# настройки редактора и системы
.vscode/
Thumbs.db
.DS_Store

# логи и временные файлы
*.log
tmp/

# локальные настройки с паролями (появятся в модуле 5)
config.local.php

# загруженные пользователями файлы (модуль 5)
uploads/*
!uploads/.gitkeep
```

Почему это важно: на GitHub люди регулярно выкладывают пароли от баз данных и ключи доступа, и боты находят их за минуты. Даже если удалить файл следующим коммитом, он останется в истории. Значит, сначала `.gitignore`, потом первый коммит. Строка `!uploads/.gitkeep` значит «кроме этого файла»: пустые папки Git не хранит, и пустой `.gitkeep` позволяет сохранить саму папку.

**Ветки.** Ветка — параллельная линия истории. Основная ветка `main` должна всегда быть рабочей. Новую функцию делаем в отдельной ветке и, когда она готова, сливаем в `main`.

```bash
git branch                      # список веток, * — текущая
git switch -c feature/docs      # создать ветку и перейти в неё
# ... правим файлы, делаем коммиты ...
git switch main                 # вернуться в main
git merge feature/docs          # влить изменения ветки в main
git branch -d feature/docs      # удалить ветку, она больше не нужна
```

`git switch` появился в Git 2.23 (2019). В старых инструкциях вы увидите `git checkout -b`, это то же самое. Если в двух ветках поменяли одну и ту же строку, при слиянии будет **конфликт**: Git вставит в файл метки `<<<<<<<`, `=======`, `>>>>>>>`. Нужно вручную оставить правильный вариант, удалить метки, сделать `git add` и `git commit`. VS Code подсвечивает конфликты и предлагает кнопки *Accept Current / Incoming / Both*.

**GitHub — облачная копия.** GitHub — сервис для хранения Git-репозиториев. Порядок такой:

1. Зарегистрироваться на github.com.
2. Нажать **New repository**, назвать, например, `portal-remont`. Галочки README и .gitignore **не ставить**: они у нас уже есть локально, иначе получите конфликт историй.
3. Связать локальный репозиторий с удалённым и отправить:

```bash
git remote add origin https://github.com/ВАШ_ЛОГИН/portal-remont.git
git push -u origin main         # -u запоминает связь, дальше хватит git push
```

При первом `push` Git for Windows через встроенный **Git Credential Manager** откроет браузер для входа в GitHub. Пароль от аккаунта в консоли больше не принимается (GitHub отключил это в 2021 году). Если менеджера нет, создайте *Personal access token* в настройках GitHub и вводите его вместо пароля.

Забрать изменения с GitHub (например, если работали дома и в колледже): `git pull`. Скачать чужой проект целиком: `git clone <url>`.

**Git в VS Code.** Вкладка *Source Control* (Ctrl+Shift+G) делает то же, что команды: «+» у файла — это `git add`, поле сообщения и галочка — `commit`, кнопка *Sync* — `pull` и `push`. Но сначала научитесь командам в терминале: так вы понимаете, что происходит, и сможете работать на любом компьютере.

**Шпаргалка: как откатиться.**

| Ситуация | Команда |
|---|---|
| Испортил файл, ещё не делал add, хочу вернуть как в последнем коммите | `git restore файл` |
| Добавил в индекс лишнее | `git restore --staged файл` |
| Посмотреть, что было в старом коммите | `git log --oneline`, затем `git show <хеш>` |
| Отменить коммит, оставив историю честной | `git revert <хеш>` |

**Типичные ошибки:**

- `git init` выполнили не в папке проекта, а в `C:\Users\...` — Git начинает следить за всем профилем. Проверяйте путь в терминале.
- Забыли `git add` и удивляетесь, что коммит пустой или «nothing to commit».
- Первый коммит сделали до `.gitignore`, и в репозиторий попал мусор. Исправление: `git rm -r --cached .vscode`, затем коммит.
- При создании репозитория на GitHub поставили галочку README, и `push` отклоняется. Решение: `git pull origin main --allow-unrelated-histories` или пересоздать пустой репозиторий.
- Работают неделю без коммитов, а потом делают один коммит «всё». Коммитьте после каждого шага, который работает.

## Задание

**Цель:** поставить сквозной проект под контроль версий и выложить его на GitHub.

**Исходные данные:** папка `C:\xampp\htdocs\portal` из ЛР1; установленный Git for Windows; аккаунт GitHub (создать на занятии, если нет).

**Ход работы:**

1. Откройте проект в VS Code, откройте терминал (`` Ctrl+` ``). Проверьте `git --version`, задайте `user.name` и `user.email`.
2. Создайте `.gitignore` по образцу из лекции. Создайте пустые папки `uploads/` с файлом `.gitkeep` и `.vscode/` с любым файлом настроек, чтобы проверить игнорирование.
3. Выполните `git init`, `git status`. Убедитесь, что `.vscode` в списке нет. Сделайте первый коммит: «Каркас портала (ЛР1)».
4. Внесите 2 осмысленных изменения в `index.php` и `style.css` (например, блок «Наши услуги» по варианту) и оформите их **двумя отдельными** коммитами с понятными сообщениями.
5. Создайте ветку `feature/docs`, в ней — папку `docs/` с файлом `requirements.md`. Перенесите туда таблицы ролей, страниц и правил из ПР1 для **своего** варианта. Сделайте коммит.
6. Вернитесь в `main`, в `index.php` поменяйте заголовок, закоммитьте. Влейте `feature/docs` в `main`.
7. **Учебный конфликт:** создайте ветку `feature/title`, измените в ней тот же заголовок `<h1>` по-другому, закоммитьте; вернитесь в `main`, измените заголовок третьим способом, закоммитьте; выполните `merge`. Разрешите конфликт в VS Code, завершите слияние коммитом.
8. Создайте пустой репозиторий на GitHub, выполните `remote add` и `push`. Обновите страницу репозитория, убедитесь, что файлы на месте, а `.vscode` нет.
9. Испортите `style.css` (удалите половину) и верните его командой `git restore`.
10. Выполните `git log --oneline --graph --all` и сделайте скриншот.

**Что сдать:** ссылку на репозиторий GitHub (можно приватный с доступом для преподавателя); скриншот `git log --oneline --graph --all`, где видны ветки и слияние; в истории не меньше 6 коммитов с осмысленными сообщениями.

## Критерии оценки

| Аспект | 2 балла | 1 балл | 0 баллов |
|---|---|---|---|
| Репозиторий и коммиты | ≥ 6 коммитов, каждое сообщение описывает изменение | Коммиты есть, но сообщения неинформативные или изменения свалены в один коммит | Репозитория нет |
| .gitignore | Создан до первого коммита, игнорируемые файлы не попали в репозиторий | Создан, но мусор в истории остался | Отсутствует |
| Ветки и слияние | Ветка `feature/docs` влита, конфликт разрешён, меток конфликта в коде нет | Слияние без конфликта или остались метки `<<<<<<<` | Веток нет |
| GitHub | Проект выложен, актуален, доступ у преподавателя | Выложен не полностью или устарел | Не выложен |
| Документация | `docs/requirements.md` по своему варианту | Скопирован пример «Мой Не Сам» | Нет |

## Если не успел / для сильных

**Минимум для зачёта:** локальный репозиторий с `.gitignore` и тремя осмысленными коммитами, выложенный на GitHub.
**Усложнение:** оформите `README.md` на GitHub (описание, скриншот, инструкция запуска на XAMPP) и сделайте лёгкий тег версии `git tag v0.1` с отправкой `git push --tags`.
