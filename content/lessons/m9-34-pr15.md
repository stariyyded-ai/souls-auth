## Лекция

**Данные живут и меняются.** Заявка не стоит на месте: сегодня она «Новая», завтра администратор переводит её «В работу», потом — «Выполнено». Клиент меняет номер телефона. Услуга дорожает. Иногда данные нужно удалить. Всё это делают две команды — `UPDATE` и `DELETE`. Они короткие, но опасные: одна пропущенная строчка — и вы перевели в «Отменено» не одну заявку, а все. Поэтому сегодня, кроме самих команд, учимся страховке: проверке перед изменением, транзакциям и ограничениям `UNIQUE`. И разберёмся, что такое индексы и почему с ними база ищет быстрее.

**UPDATE — изменить существующие строки.**

```sql
UPDATE requests
SET status_id = 2
WHERE id = 3;
```

Читается как «в таблице заявок поставь статус 2 там, где номер 3». В `SET` можно менять несколько полей через запятую — именно так администратор отменяет заявку с причиной:

```sql
UPDATE requests
SET status_id = 4,
    cancel_reason = 'Клиент передумал'
WHERE id = 15 AND status_id = 1;
```

Обратите внимание на второе условие `AND status_id = 1`: отменить можно только новую заявку. Если заявка уже выполнена, запрос ничего не изменит, и phpMyAdmin напишет «Затронуто 0 строк». В PHP это проверяется через количество изменённых строк (`rowCount()`), и пользователю показывается понятное сообщение. Это хороший приём: бизнес-правило ТЗ записано прямо в `WHERE`.

В `SET` можно использовать текущее значение поля:

```sql
UPDATE services SET price = price * 1.1 WHERE price < 3000;  -- +10% дешёвым услугам
```

**Золотое правило UPDATE и DELETE.** Запрос без `WHERE` меняет **все строки таблицы**:

```sql
UPDATE requests SET status_id = 4;   -- все заявки портала стали «Отменено»
```

Отмены (Ctrl+Z) в базе нет. Поэтому привычка на всю жизнь: **сначала `SELECT` с тем же `WHERE`, потом `UPDATE`/`DELETE`**.

```sql
SELECT id, status_id FROM requests WHERE id = 15 AND status_id = 1;  -- 1 строка? та самая?
UPDATE requests SET status_id = 4, cancel_reason = 'Клиент передумал'
WHERE id = 15 AND status_id = 1;
```

Увидели одну нужную строку — меняете. Увидели 15 — остановились и думаете.

**DELETE — удалить строки.**

```sql
DELETE FROM services WHERE name = 'Мойка окон';
```

Здесь включаются правила внешних ключей из ПР13:

- Услугу «Общий клининг» удалить нельзя: на неё ссылаются заявки, а у связи стоит `RESTRICT`. Ответ — `#1451 Cannot delete or update a parent row`. Это не баг, это защита: иначе в истории заявок появились бы заявки на «неизвестную» услугу.
- Пользователя удалить можно, и вместе с ним каскадом (`CASCADE`) удалятся все его заявки. В учебной базе удаление `smirnov_d` уменьшает число заявок с 15 до 11. Удобно, но опасно: в реальных системах клиентов часто не удаляют, а помечают полем `is_blocked`.

`TRUNCATE TABLE имя` очищает таблицу целиком и сбрасывает счётчик `AUTO_INCREMENT` на 1. На таблицу, на которую ссылаются внешние ключи (`statuses`, `users`), он не сработает: ошибка `#1701`. На практике `DELETE … WHERE` — ваш основной инструмент, а `TRUNCATE` — для очистки тестовой таблицы перед повторным импортом.

**Транзакции — «всё или ничего».** Представьте перевод денег с карты на карту: списать с одной и зачислить на другую. Если между двумя действиями пропал свет, деньги не должны исчезнуть. Для этого несколько запросов объединяют в **транзакцию**:

```sql
START TRANSACTION;
UPDATE requests SET status_id = 4, cancel_reason = 'Тест транзакции' WHERE status_id = 1;
SELECT COUNT(*) FROM requests WHERE status_id = 4;   -- видим результат «как будто»
ROLLBACK;                                            -- передумали: всё вернулось
SELECT COUNT(*) FROM requests WHERE status_id = 4;   -- как было до START
```

- `START TRANSACTION` — начать;
- `COMMIT` — зафиксировать все изменения навсегда;
- `ROLLBACK` — отменить все изменения с начала транзакции.

Без `START TRANSACTION` MySQL работает в режиме **автофиксации**: каждый запрос сразу сохраняется навсегда. Транзакции работают только в InnoDB (ещё одна причина выбирать его). Важная деталь phpMyAdmin: каждая кнопка «Вперёд» — это отдельное подключение к серверу. Поэтому `START TRANSACTION`, изменения и `ROLLBACK`/`COMMIT` нужно отправлять **одним блоком** на вкладке SQL; если выполнить `START TRANSACTION` отдельно, а через минуту отдельно `ROLLBACK`, отката не будет. В PHP то же делают методы `$pdo->beginTransaction()`, `commit()`, `rollBack()` — например, когда при смене статуса нужно ещё и записать строку в журнал изменений.

**UNIQUE — запрет повторов.** Уникальное ограничение мы уже ставили на логин. Его можно добавить и к готовой таблице:

```sql
ALTER TABLE users ADD UNIQUE KEY uq_users_email (email);
```

Если в таблице уже есть повторы, команда не выполнится — сначала уберите дубли. После этого попытка вставить существующий email даст `#1062 Duplicate entry 'ivanov@mail.ru' for key 'uq_users_email'`.

Интересный эффект сравнения `utf8mb4_unicode_ci` (регистронезависимого): логин `IVANOV_A` тоже не вставится, потому что для базы он совпадает с `ivanov_a`. Для логинов это как раз то, что нужно.

`UNIQUE` бывает составным — по нескольким столбцам. Например, если в варианте «бронь столиков» хранятся конкретные столики (таблица `restaurant_tables`, а в брони — поле `table_id`), один столик нельзя забронировать дважды на одно время:

```sql
ALTER TABLE bookings ADD UNIQUE KEY uq_table_slot (table_id, booking_date, booking_time);
```

Порознь значения могут повторяться, а вот тройка целиком — нет.

**Индексы — оглавление для таблицы.** Как найти тему в учебнике на 500 страниц? Можно листать всё подряд, а можно открыть предметный указатель в конце. **Индекс** — такой указатель для столбца: СУБД заранее сортирует значения и знает, где какое лежит. Первичный ключ и `UNIQUE` — это индексы, и для каждого внешнего ключа InnoDB тоже создаёт индекс сам (посмотрите «Структура» → «Индексы» у `requests`: там `fk_requests_user`, `fk_requests_status` и др.). Свой индекс добавляют на столбцы, по которым часто ищут или сортируют:

```sql
CREATE INDEX idx_requests_service_date ON requests (service_date);
```

Проверить, использует ли запрос индекс, помогает `EXPLAIN`:

```sql
EXPLAIN SELECT id FROM requests WHERE service_date = '2026-10-25';
```

В столбце `key` будет `idx_requests_service_date`, а в `type` — `ref`. Если `key` пустой, а `type` = `ALL`, значит, база читает всю таблицу подряд. На 15 строках разницы не видно, на 150 000 — секунды против миллисекунд. Но индекс не бесплатный: он занимает место и замедляет `INSERT`/`UPDATE`, поэтому индексы «на всякий случай» на все столбцы не ставят.

**Типичные ошибки:**

1. `UPDATE`/`DELETE` без `WHERE` — изменена вся таблица.
2. Выделили мышкой в редакторе SQL только первую строку запроса, а `WHERE` осталось за выделением, — phpMyAdmin выполнил выделенное.
3. `WHERE status = 'Отменено'` в `requests`, где статус хранится числом `status_id`.
4. Попытка удалить услугу или статус, на которые есть заявки, — `#1451`; решение не «отключить ключи», а сначала решить, что делать с заявками.
5. `START TRANSACTION` и `ROLLBACK` выполнены разными нажатиями «Вперёд» в phpMyAdmin.
6. Добавление `UNIQUE` на столбец, где уже есть повторы, — ошибка `#1062` при `ALTER TABLE`.

**Связь с экзаменом.** Смена статуса заявки и отмена с указанием причины в админ-панели — обязательная часть задания 1, и это `UPDATE` с правильным `WHERE`. Уникальность логина проверяет эксперт, пытаясь зарегистрироваться повторно, — `UNIQUE` гарантирует результат, даже если PHP-проверка не сработала. Эти вещи прямо влияют на аспекты «разработка модулей ИС по ТЗ» и «безопасность ИС».
