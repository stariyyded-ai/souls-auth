## Лекция

**Каждая страница — это запрос.** Откройте любое приложение, которым пользуетесь каждый день: «Госуслуги», банк, такси. Экран «Мои заявления» или «История поездок» — это один SQL-запрос, результат которого программист красиво разложил по карточкам. На экзамене страниц немного, и запросы к ним всегда одни и те же. Наша задача сегодня — написать и отладить их **заранее, прямо в phpMyAdmin**, до того как появится PHP. Тогда в модуле 5 вы будете не придумывать SQL и PHP одновременно, а просто переносить проверенный запрос в код.

**Карта: страница → запрос.**

| Страница портала | Что делает с БД | Запрос |
|---|---|---|
| Регистрация | проверить, свободен ли логин; добавить пользователя | `SELECT` + `INSERT INTO users` |
| Вход | найти пользователя по логину, получить хеш и роль | `SELECT … WHERE login = …` |
| Новая заявка | показать списки услуг и способов оплаты; сохранить заявку | 2 × `SELECT` + `INSERT INTO requests` |
| Мои заявки | заявки текущего пользователя со статусами | `SELECT … JOIN … WHERE user_id = …` |
| Админ-панель | все заявки с ФИО и контактами, фильтр по статусу | `SELECT … JOIN users … WHERE status_id = …` |
| Смена статуса | изменить статус и причину отмены | `UPDATE` (в ПР15) |

**Значения «снаружи».** В phpMyAdmin мы пишем конкретные значения: `WHERE user_id = 3`. В PHP на их месте будут данные из сессии или формы. Подставлять их склейкой строк нельзя — это SQL-инъекция, разберём в ПР19. Правильно — через **параметры**: в запросе ставится метка `:user_id`, а значение передаётся отдельно. Поэтому сегодня в файле запросов будем подписывать, какое значение придёт снаружи:

```sql
-- Мои заявки. Снаружи: :user_id (из сессии)
... WHERE r.user_id = 3   -- 3 заменится на :user_id
```

**Регистрация.**

```sql
-- Проверка: занят ли логин. Снаружи: :login
SELECT COUNT(*) AS cnt FROM users WHERE login = 'ivanov_a';
-- 1 — занят, показываем «Пользователь с таким логином уже существует»

-- Сохранение. Снаружи: все поля формы, пароль — уже хеш из password_hash()
INSERT INTO users (login, password, full_name, phone, email)
VALUES ('novikov_v', '$2y$10$EJkOXBoeT9jIG81Wrpo...ca3by5XwO08Zkln897D6tcsewNzxWye',
        'Новиков Виктор Ильич', '+7(915)-111-22-33', 'novikov@mail.ru');
```

`role` и `created_at` не передаём — сработают умолчания. Даже если PHP «забудет» проверить логин, `UNIQUE` в базе не пустит дубль: это вторая линия защиты.

**Вход.**

```sql
-- Снаружи: :login
SELECT id, password, role, full_name FROM users WHERE login = 'adminka';
```

Заметьте: мы **не** пишем `WHERE login = … AND password = …`. Хеш нельзя сравнить со введённым паролем в SQL: PHP достаёт хеш по логину и проверяет его функцией `password_verify()`. Из того же запроса берём `role`: `admin` — пускаем в админ-панель, `user` — в личный кабинет.

**Новая заявка.** Сначала заполняем выпадающие списки формы:

```sql
SELECT id, name, price FROM services ORDER BY name;
SELECT id, name FROM payment_types ORDER BY id;
```

В `<select>` значением `<option>` будет `id`, а текстом — `name`. Пользователь видит «Генеральная уборка», а в базу уходит `2`.

Сохранение:

```sql
-- Снаружи: :user_id (из сессии), остальное из формы
INSERT INTO requests (user_id, service_id, payment_type_id, address, contact_phone, service_date, service_time)
VALUES (7, 1, 2, 'ул. Цветочная, 8, кв. 3', '+7(901)-765-43-21', '2026-11-02', '10:00:00');
```

`status_id` не передаём: умолчание `1` = «Новая». Это требование почти любого ТЗ — новая заявка создаётся в статусе «Новая», и пользователь сам его выбрать не может. `user_id` берётся из сессии, а не из формы: иначе хитрый пользователь в DevTools поменяет скрытое поле и создаст заявку от чужого имени.

**Мои заявки.**

```sql
-- Снаружи: :user_id
SELECT r.id, s.name AS service, r.service_date, r.service_time, r.address,
       p.name AS payment, st.name AS status, r.cancel_reason
FROM requests r
JOIN services      s  ON s.id  = r.service_id
JOIN payment_types p  ON p.id  = r.payment_type_id
JOIN statuses      st ON st.id = r.status_id
WHERE r.user_id = 3
ORDER BY r.created_at DESC;
```

Для `petrova_m` (`id = 3`) получим три заявки: 6 «Генеральная уборка» — Новая, 5 «Послестроительная уборка» — В работе, 4 «Общий клининг» — Отменено с причиной «Клиент перенёс ремонт». Новые сверху — так привыкли пользователи любых сервисов.

**Админ-панель: все заявки с ФИО.**

```sql
SELECT r.id, u.full_name, u.phone, u.email,
       s.name AS service, r.address, r.service_date, r.service_time,
       p.name AS payment, st.name AS status, r.cancel_reason
FROM requests r
JOIN users         u  ON u.id  = r.user_id
JOIN services      s  ON s.id  = r.service_id
JOIN payment_types p  ON p.id  = r.payment_type_id
JOIN statuses      st ON st.id = r.status_id
ORDER BY r.created_at DESC;
```

Это самый длинный запрос модуля, но он собран из уже знакомых кусков: четыре `JOIN` по схеме «PK родителя = FK заявки».

**Фильтр по статусу** — тот же запрос плюс одна строка перед `ORDER BY`:

```sql
WHERE r.status_id = 1   -- снаружи: :status_id из <select> фильтра
```

Для «Новых» в учебной базе это заявки 12, 15, 6, 3 (в таком порядке — новые сверху). Список статусов для фильтра — `SELECT id, name FROM statuses ORDER BY id;`.

**Счётчики для админки** («Новых: 4, в работе: 2 …»):

```sql
SELECT st.id, st.name, COUNT(r.id) AS total
FROM statuses st
LEFT JOIN requests r ON r.status_id = st.id
GROUP BY st.id, st.name
ORDER BY st.id;
```

`LEFT JOIN` нужен, чтобы статус без заявок показал 0, а не пропал.

**Пагинация** (пригодится в ЛР30): страница 2 по 5 заявок — `LIMIT 5 OFFSET 5`. В учебной базе это заявки 11, 14, 9, 13, 8.

**Поиск по ФИО:**

```sql
WHERE u.full_name LIKE '%петров%'
```

Внимание, сюрприз: запрос найдёт не только Петрову, но и Иванова Алексея **Петровича** — отчество тоже содержит «петров». Поиск по подстроке всегда шире, чем кажется; тестируйте его на реальных данных.

**Как хранить запросы.** Заведите в проекте файл `db/queries.sql`. Каждый запрос — с шапкой-комментарием: для какой страницы, какие значения придут снаружи, что ожидается в учебной базе. В модуле 5 вы будете открывать этот файл и копировать запросы в PHP, заменяя числа на `:метки`.

**Типичные ошибки:**

1. В «Моих заявках» нет фильтра `WHERE user_id = …` — пользователь видит чужие заявки. На экзамене это одновременно ошибка функциональности и безопасности.
2. Вход через `WHERE login = … AND password = …` — с хешами так не работает.
3. `status_id` передаётся из формы создания заявки — пользователь сам ставит себе «Выполнено».
4. В админке вместо ФИО — `user_id`, вместо статуса — цифра. ТЗ требует видеть ФИО и контакты.
5. Нет сортировки — порядок строк без `ORDER BY` не гарантирован, сегодня одно, завтра другое.
6. `SELECT *` при `JOIN` нескольких таблиц: столбцы `id` и `name` повторяются, и в PHP останется только последний.

**Связь с экзаменом.** Требования задания 1 по ТЗ — «пользователь видит свои заявки со статусами», «администратор видит все заявки с ФИО и контактами, меняет статус» — это ровно эти запросы. Аспект «разработка модулей ИС по ТЗ» засчитывается, когда страница показывает правильные данные; правильные данные — это правильный `SELECT`.

## Задание

**Цель:** написать и отладить в phpMyAdmin все запросы, которые понадобятся страницам вашего портала, и сохранить их в `db/queries.sql`.

**Исходные данные:** ваша наполненная база из ЛР18 (11 пользователей, 20 заявок); учебная база `portal_training` для сверки с эталонами из лекции.

**Ход работы:**

1. Создайте файл `db/queries.sql` и шаблон шапки для каждого запроса:
   ```sql
   -- [Страница] Мои заявки
   -- [Снаружи] :user_id — из сессии
   -- [Ожидается] для belova_t (id=2): 2 строки
   ```
2. **Регистрация.** Запрос проверки логина. Проверьте на занятом (`belova_t`) и свободном логине. Запрос `INSERT` нового пользователя (возьмите хеш из ЛР18).
3. **Вход.** Запрос по логину, возвращающий `id`, `password`, `role`, `full_name`. Проверьте для `adminka` и для обычного пользователя.
4. **Новая заявка.** Два запроса для списков и `INSERT` заявки без `status_id` и без `created_at`. Убедитесь, что новая заявка получила статус «Новая».
5. **Мои заявки.** Запрос со всеми `JOIN`, фильтром по `user_id`, сортировкой новыми сверху. Проверьте на двух пользователях, у одного из которых есть отменённая заявка (`volkov_s`).
6. **Админ-панель.** Все заявки с ФИО, телефоном, email, услугой, датой, временем, оплатой, статусом и причиной отмены. Проверьте: строк столько же, сколько в `requests` (`SELECT COUNT(*) FROM requests`).
7. **Фильтр по статусу.** Тот же запрос с `WHERE r.status_id = …`. Проверьте на каждом из 4 статусов, сумма строк должна совпасть с общим числом.
8. **Счётчики статусов** с `LEFT JOIN`. Добавьте временно статус «Архив» и убедитесь, что он показывается с нулём; потом удалите его.
9. **Пагинация.** Вторая страница админки по 5 заявок.
10. **Поиск по ФИО.** Найдите все заявки клиентов, в ФИО которых есть «ов». Объясните в комментарии, почему результатов так много.
11. Перепроверьте запросы 5–7 на `portal_training`: результаты должны совпасть с примерами лекции.
12. Закоммитьте `db/queries.sql`.

**Что сдать:** `db/queries.sql` — не меньше 12 запросов с шапками; скриншоты результатов «Мои заявки» и «Админ-панель с фильтром».

## Критерии оценки

| Аспект | 2 балла | 1 балл | 0 баллов |
|---|---|---|---|
| Регистрация и вход | проверка логина, INSERT без роли и даты, вход по логину без сравнения пароля в SQL | один запрос с ошибкой | запросов нет или вход через `password = …` |
| Новая заявка | списки из справочников, INSERT без `status_id`, статус по умолчанию «Новая» | INSERT передаёт `status_id` | нет |
| Мои заявки | фильтр по пользователю, статусы и услуги текстом, сортировка | нет сортировки или вместо текста id | нет фильтра по пользователю |
| Админ-панель и фильтр | все заявки с ФИО и контактами, фильтр по статусу, счётчики с нулями | одно из трёх отсутствует | только `SELECT * FROM requests` |
| Оформление `queries.sql` | у каждого запроса шапка: страница, внешние значения, ожидание | шапки частично | без комментариев |

## Если не успел / для сильных

**Минимум для зачёта:** запросы «Мои заявки», «Админ-панель» и фильтр по статусу, проверенные на вашей базе.
**Усложнение:** создайте представление `CREATE VIEW v_admin_requests AS …` с запросом админ-панели и перепишите фильтр и поиск как `SELECT … FROM v_admin_requests WHERE …`; объясните в комментарии плюсы и минусы такого подхода.

:::quiz
? Почему при входе не пишут `WHERE login = ... AND password = ...`?
- [ ] Так запрос работает слишком медленно
- [ ] В `WHERE` нельзя использовать два условия
- [x] В базе хеш, его нельзя сравнить с паролем в SQL — проверяет `password_verify()`
- [ ] Пароль хранится в отдельной таблице
> По логину достают хеш и роль, а совпадение пароля проверяет PHP функцией `password_verify()`.

? Откуда берётся `user_id` для новой заявки?
- [x] Из сессии, иначе пользователь подменит его и создаст заявку от чужого имени
- [ ] Из скрытого поля формы, так удобнее всего
- [ ] Его вводит сам пользователь в форме
- [ ] Его не передают, база подставит сама по умолчанию
> Всё, что приходит из формы, можно поменять в DevTools, поэтому кто создаёт заявку, берут из сессии.

? Зачем в счётчиках статусов используют `LEFT JOIN` и `COUNT(r.id)`?
- [ ] Чтобы запрос выполнялся быстрее
- [ ] Чтобы не считать отменённые заявки
- [ ] Чтобы статусы шли в порядке номеров
- [x] Чтобы статус без заявок показал 0, а не пропал или получил 1
> `LEFT JOIN` сохраняет статус без заявок, а `COUNT(r.id)` не считает строку с `NULL`, поэтому выходит 0.

? Чем запрос «Мои заявки» отличается от запроса админ-панели?
- [ ] В «Моих заявках» нет `JOIN` со справочниками
- [x] В нём есть `WHERE r.user_id = ...`, а `JOIN users` с ФИО не нужен
- [ ] В нём сортировка от старых к новым
- [ ] Он берёт данные из другой таблицы
> Оба запроса собраны из одних `JOIN`; админке нужны ФИО и контакты всех клиентов, а пользователю — только свои заявки.
