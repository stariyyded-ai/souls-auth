## Лекция

На прошлой практике вы научились подключаться к серверу и подготовили проект. Сегодня — настоящий деплой вашего портала заявок от начала до конца, плюс то, что обычно ломается и как это чинить без паники. Лекция короткая по теории и длинная по практике: читайте её как инструкцию, к которой вы будете возвращаться весь урок.

**Порядок деплоя, который работает всегда.** Профессионалы деплоят по одному и тому же сценарию, чтобы ничего не забыть. Наш сценарий из девяти шагов:

1. **Заморозить локальную версию.** Проверить, что в XAMPP всё работает, сделать `git commit` с сообщением «release 1.0». Если что-то сломается на сервере, вы будете знать, с чем сравнивать.
2. **Сделать дамп БД** (utf8mb4, без `CREATE DATABASE` и `USE`).
3. **Создать/проверить базу на сервере** и узнать четыре параметра: хост, имя базы, пользователь, пароль.
4. **Импортировать дамп** через phpMyAdmin хостинга или `mysql ... < dump.sql`.
5. **Подготовить серверный `config.php`** с новыми параметрами и `display_errors = 0`.
6. **Залить файлы** по SFTP (или `git clone`/`git pull`) в корневую папку сайта.
7. **Выставить права** 755 на папки, 644 на файлы, проверить запись в `uploads/`.
8. **Пройти сценарий проверки** (гость → пользователь → администратор).
9. **Зафиксировать результат:** ссылка, скриншоты, запись в README.

Обратите внимание: база импортируется **до** файлов. Если сделать наоборот, в промежутке сайт будет показывать ошибку подключения каждому, кто его откроет. Для учебного проекта это не страшно, а в реальной работе — это минуты простоя у заказчика.

**Как заливать только изменения.** После первого деплоя вы найдёте баги и будете их исправлять. Перезаливать весь проект каждый раз долго и опасно — можно затереть серверный `config.php` локальным. Правила:

- В FileZilla при перезаписи выбирайте «Перезаписать, если источник новее», а `config.php` исключите (*Вид → Фильтры имён файлов*).
- Если деплой через Git — на сервере просто `cd ~/public_html && git pull`. Поскольку `config.php` в `.gitignore`, он не затрётся.
- Изменения в структуре БД (новый столбец, новая таблица) переносите отдельным SQL-скриптом, а не полным дампом: полный дамп с `DROP TABLE` удалит заявки, которые уже создали реальные пользователи.

**Файл .htaccess: маленькие полезные настройки.** На хостингах с Apache в корне сайта можно положить файл `.htaccess`. Для нашего портала пригодится:

```apache
# Главная страница по умолчанию
DirectoryIndex index.php

# Запрет просмотра списка файлов в папках
Options -Indexes

# Закрыть служебные файлы от браузера
<FilesMatch "^(config\.php|.*\.sql|\.env)$">
    Require all denied
</FilesMatch>

# Перенаправление на HTTPS (включать, только если сертификат уже выпущен)
RewriteEngine On
RewriteCond %{HTTPS} off
RewriteRule ^ https://%{HTTP_HOST}%{REQUEST_URI} [L,R=301]
```

Почему важно закрыть `config.php`, если PHP-файл и так выполняется, а не показывается? Потому что если на сервере сломается обработчик PHP, браузер покажет исходный код — вместе с паролем к базе. Это редкость, но защита стоит одной строки. А `Options -Indexes` не даст посмотреть содержимое папки `uploads/` простым переходом по адресу.

Ещё надёжнее — держать `config.php` **выше** корня сайта (`~/config.php`, а в коде `require __DIR__ . '/../config.php';`). Тогда его в принципе нельзя открыть из браузера.

**HTTPS.** Без HTTPS пароль пользователя при входе передаётся открытым текстом, а браузер помечает форму «Не защищено». Почти все хостинги выдают бесплатный сертификат Let's Encrypt одной кнопкой в панели («SSL-сертификаты → Выпустить»). На VPS это делает утилита `certbot`. После выпуска включите перенаправление на HTTPS из `.htaccess` выше и проверьте, что стили и скрипты подключены относительными путями — иначе браузер заблокирует «смешанное содержимое» (CSS по `http://` на странице `https://`).

**Разбор частых ошибок на сервере.** Сохраните себе эту таблицу — она экономит часы.

| Симптом | Скорее всего | Как проверить и исправить |
|---|---|---|
| Белый экран | Фатальная ошибка PHP, ошибки скрыты | Лог ошибок хостинга; временно `display_errors=1` |
| `SQLSTATE[HY000] [1045] Access denied` | Неверный логин/пароль БД | Сверить `config.php` с панелью хостинга |
| `[1049] Unknown database` | Не та база или не импортирована | `SHOW DATABASES;` / имя в панели |
| `[2002] Connection refused` | Неверный DB_HOST | Узнать хост в панели (иногда не `localhost`) |
| `Table '...users' doesn't exist` | Дамп не импортирован или регистр имени таблицы | `SHOW TABLES;`, на Linux `Users` ≠ `users` |
| «????» или «Ð¡Ð» вместо кириллицы | Кодировка дампа или подключения | В DSN `charset=utf8mb4`, дамп в utf8mb4 |
| Нет стилей, 404 в Network | Абсолютный путь `/portal/css/...` или регистр | Сделать пути относительными / через `BASE_URL` |
| 403 Forbidden | Права или нет `index.php` | `chmod 644`/`755`, `DirectoryIndex` |
| `Cannot modify header information` | Вывод до `header()`: пробел, BOM | Убрать пробелы до `<?php`, сохранить в UTF-8 без BOM |
| Сессия «вылетает» после входа | Нет `session_start()` до вывода | Первой строкой в общем файле |
| Не загружаются файлы | Нет прав на `uploads/` или лимит размера | Права, `upload_max_filesize` в панели |

Ошибка `Cannot modify header information` — классика деплоя: в Windows редактор мог сохранить файл с невидимой меткой BOM. В VS Code внизу справа видна кодировка: должно быть `UTF-8`, а не `UTF-8 with BOM`.

**Проверка по ролям.** Делайте проверку в двух браузерах (или в обычном окне и инкогнито): в одном — пользователь, в другом — администратор. Так вы сразу увидите, что администратор меняет статус, а пользователь после обновления страницы видит новый статус. Отдельно попробуйте:

- открыть `admin.php` без входа и под обычным пользователем — должен быть редирект или «Доступ запрещён»;
- ввести в поле ФИО `<script>alert(1)</script>` — в списке заявок должен отобразиться текст, а не всплыть окно (проверка `htmlspecialchars`);
- ввести логин `' OR 1=1 --` при входе — должна быть ошибка «неверные данные» (проверка prepared statements).

Это те же проверки, которые на экзамене проходит эксперт по критерию «безопасность ИС».

**README деплоя.** Последний шаг — короткая инструкция в `README.md` репозитория: адрес сайта, требования (PHP 8.2, MySQL 8 / MariaDB 10.4+), как импортировать дамп, какой файл переименовать в `config.php`, учётка администратора. Через полгода вы скажете себе спасибо, а работодатель на собеседовании увидит, что вы умеете не только писать код, но и доводить его до пользователя.

## Задание

**Цель:** опубликовать свой портал заявок на удалённом сервере так, чтобы все роли и сценарии работали по внешней ссылке.

**Ход работы:**
1. Проверьте проект локально, сделайте коммит «release 1.0».
2. Сделайте дамп БД (utf8mb4, без `CREATE DATABASE`/`USE`), убедитесь, что в `users` есть `adminka`.
3. Импортируйте дамп на сервер (phpMyAdmin или `mysql` по SSH), выполните `SHOW TABLES;` и `SELECT login FROM users;` — скриншот.
4. Создайте серверный `config.php` (данные БД сервера, `display_errors=0`, `BASE_URL`).
5. Залейте файлы по SFTP или через `git clone`. Исключите `.git`, `.vscode`, `*.sql`.
6. Выставьте права: папки 755, файлы 644; проверьте запись в `uploads/`, если она есть.
7. Добавьте `.htaccess` с `Options -Indexes` и закрытием служебных файлов. Если хостинг даёт сертификат — включите HTTPS.
8. Пройдите сценарий проверки по ролям (гость, пользователь, администратор) и три проверки безопасности из лекции. Каждый найденный дефект запишите и исправьте, перезалив только изменённый файл.
9. Допишите в `README.md` раздел «Развёртывание».

**Что сдать:** ссылку на работающий сайт; протокол проверки (таблица: шаг → ожидание → результат, со скриншотами); список найденных и исправленных дефектов; ссылку на репозиторий с README.

## Критерии оценки

| Аспект | 2 балла | 1 балл | 0 баллов |
|---|---|---|---|
| Сайт доступен по ссылке | Открывается, стили и картинки на месте, нет 404 | Открывается с отдельными ошибками | Не открывается |
| Перенос БД | Все таблицы и данные, кириллица корректна, админ входит | Таблицы есть, но проблемы с данными/кодировкой | БД не перенесена |
| Работа ролей и сценариев | Регистрация, вход, заявка, смена статуса работают | Работает часть сценариев | Сценарии не работают |
| Безопасность публикации | `display_errors=0`, пароли не в Git, `-Indexes`, нет 777, проверки XSS/SQL пройдены | Выполнена половина пунктов | Не выполнено |
| Протокол и README | Полный протокол со скриншотами, README с инструкцией | Протокол неполный или нет README | Нет отчётности |

## Если не успел / для сильных

**Минимум для зачёта:** сайт открывается по ссылке, БД перенесена, пользователь может зарегистрироваться и войти.
**Усложнение:** HTTPS с редиректом, `config.php` вынесен выше корня сайта, обновление через `git pull` по SSH.
