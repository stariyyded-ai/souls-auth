## Лекция

**Проблема: HTTP ничего не помнит.** Каждый запрос браузера к серверу — как звонок в справочную, где каждый раз отвечает новый оператор. Вы вошли на `login.php`, перешли на `requests.php` — а сервер уже «забыл», кто вы. Чтобы портал понимал «это снова Иванов, он уже ввёл пароль», нужны **cookies** и **сессии**.

**Cookie** — маленький текстовый файл, который сервер просит браузер сохранить и затем присылать с **каждым** запросом к этому сайту. Хранится **у пользователя**, а значит, пользователь может его прочитать и изменить (DevTools → Application → Cookies).

```php
<?php
// practice/theme.php — запоминаем выбранную тему на 30 дней
if (isset($_GET['theme']) && in_array($_GET['theme'], ['light', 'dark'], true)) {
    setcookie('theme', $_GET['theme'], [
        'expires'  => time() + 60 * 60 * 24 * 30,
        'path'     => '/',
        'httponly' => true,
        'samesite' => 'Lax',
    ]);
    header('Location: theme.php');
    exit;
}
$theme = $_COOKIE['theme'] ?? 'light';
$theme = in_array($theme, ['light', 'dark'], true) ? $theme : 'light';
?>
<body style="background: <?= $theme === 'dark' ? '#222; color:#eee' : '#fff' ?>">
    <p>Текущая тема: <?= $theme ?></p>
    <a href="?theme=light">Светлая</a> | <a href="?theme=dark">Тёмная</a>
</body>
```

Важно: `setcookie()`, как и `header()`, работает только **до** любого вывода. И cookie появится в `$_COOKIE` только при **следующем** запросе — поэтому после установки делаем редирект. Обратите внимание, что значение cookie мы проверяем по «белому списку» (`light`/`dark`): раз его может подменить пользователь, это такие же недоверенные данные, как поля формы.

**Можно ли хранить в cookie, что пользователь — администратор?** Нет! Если записать `setcookie('role', 'admin')`, любой поменяет значение в DevTools и станет админом. Для этого и нужны сессии.

**Сессия** — хранилище данных **на сервере**. Браузеру отдаётся только cookie с длинным случайным идентификатором (`PHPSESSID=k3j4h5...`). По этому номеру PHP находит на сервере «папку» с данными пользователя. Пользователь видит номер, но не содержимое и подменить роль не может.

```php
<?php
// practice/counter.php — счётчик посещений в сессии
session_start();                               // ВСЕГДА до любого вывода

$_SESSION['visits'] = ($_SESSION['visits'] ?? 0) + 1;
echo 'Вы открыли эту страницу ' . $_SESSION['visits'] . ' раз(а).<br>';
echo 'ID сессии: ' . session_id();
```

Обновите страницу несколько раз — число растёт. Откройте её в режиме инкогнито — счёт начнётся с 1: там другая сессия. Удалите cookie `PHPSESSID` в DevTools — сессия «потеряется».

Основные действия с сессией:

| Действие | Код |
|---|---|
| Запустить / продолжить | `session_start();` (у нас — в `config.php`) |
| Записать | `$_SESSION['user'] = [...];` |
| Прочитать | `$_SESSION['user'] ?? null` |
| Удалить одно значение | `unset($_SESSION['flash']);` |
| Сменить ID (при входе!) | `session_regenerate_id(true);` |
| Полностью завершить | `$_SESSION = []; session_destroy();` + удалить cookie |

**Что хранить в сессии после входа.** В нашем портале — массив `$_SESSION['user']` с полями `id`, `login`, `fio`, `role`. **Пароль и его хеш в сессию не кладём** — они там не нужны. `id` нужен, чтобы в запросах писать `WHERE user_id = ?`, `role` — чтобы решать, что показывать.

**Фиксация сессии и `session_regenerate_id()`.** Атака «фиксация сессии»: злоумышленник заранее подсовывает жертве известный ему ID сессии, жертва входит — и злоумышленник с тем же ID оказывается внутри. Защита — сразу после успешного входа выдать **новый** ID: `session_regenerate_id(true)`. Одна строка, а на экзамене это заметный плюс к безопасности.

**Роли.** Роль — это ответ на вопрос «что этому человеку можно». В портале их две:

- `user` — создаёт свои заявки и видит только свои;
- `admin` — видит все заявки и меняет их статус.

Роль хранится в базе (столбец `users.role`), при входе копируется в сессию, а **каждая** защищённая страница её проверяет. Скрыть ссылку на админку в меню — недостаточно: экзаменатор просто наберёт `admin.php` в адресной строке.

**Мини-демо: вход с ролями без базы** (`practice/mini_login.php`). Пользователи заданы массивом, чтобы сосредоточиться на сессии; в портале они будут в БД.

```php
<?php
session_start();

// В реальности хеши лежат в базе; здесь считаем их при запуске для простоты.
$users = [
    'student1' => ['hash' => password_hash('qwerty1', PASSWORD_DEFAULT), 'role' => 'user'],
    'adminka'  => ['hash' => password_hash('password', PASSWORD_DEFAULT), 'role' => 'admin'],
];

$error = '';
if ($_SERVER['REQUEST_METHOD'] === 'POST') {
    $login = is_string($_POST['login'] ?? null) ? trim($_POST['login']) : '';
    $pass  = is_string($_POST['password'] ?? null) ? $_POST['password'] : '';

    if (isset($users[$login]) && password_verify($pass, $users[$login]['hash'])) {
        session_regenerate_id(true);
        $_SESSION['user'] = ['login' => $login, 'role' => $users[$login]['role']];
        header('Location: mini_login.php');
        exit;
    }
    $error = 'Неверный логин или пароль';
}

if (isset($_GET['logout'])) {
    $_SESSION = [];
    session_destroy();
    header('Location: mini_login.php');
    exit;
}

$user = $_SESSION['user'] ?? null;
?>
<!doctype html><html lang="ru"><head><meta charset="utf-8"><title>Мини-вход</title></head><body>
<?php if ($user): ?>
    <p>Вы вошли как <b><?= htmlspecialchars($user['login']) ?></b>, роль: <?= $user['role'] ?></p>
    <?php if ($user['role'] === 'admin'): ?>
        <p style="color:green">Секретный раздел администратора</p>
    <?php else: ?>
        <p>Раздел обычного пользователя</p>
    <?php endif; ?>
    <a href="?logout=1">Выйти</a>
<?php else: ?>
    <p style="color:red"><?= htmlspecialchars($error) ?></p>
    <form method="post">
        <input name="login" placeholder="Логин">
        <input name="password" type="password" placeholder="Пароль">
        <button>Войти</button>
    </form>
<?php endif; ?>
</body></html>
```

Обратите внимание на сообщение об ошибке: «Неверный логин **или** пароль». Мы не говорим, что именно неверно, — иначе злоумышленник сможет перебором узнать, какие логины существуют.

**Как сессия хранится физически.** В XAMPP — файлы в `C:\xampp\tmp\sess_...`. Откройте один в Блокноте — увидите сериализованный массив. Поэтому чем меньше в сессии лишнего, тем лучше.

**Типичные ошибки.**

- `session_start(): Session cannot be started after headers have already been sent` — перед `session_start()` был вывод (даже пробел или BOM в начале файла). В портале сессию стартует только `config.php`, который подключается первым.
- `Undefined array key "user"` — читаете `$_SESSION['user']` без `?? null`.
- После выхода пользователь всё ещё «внутри» — забыли очистить `$_SESSION` или делаете выход без редиректа.
- Роль проверяется только в меню, а не на странице.

**Связь с экзаменом.** Вход и выход, разные меню для гостя, пользователя и администратора, запрет доступа к `admin.php` обычному пользователю — всё держится на сессии. Это аспекты и «разработки модулей ИС», и «безопасности ИС».

## Задание

**Цель:** понять разницу между cookie и сессией, научиться хранить данные пользователя в сессии и разграничивать доступ по ролям.

**Ход работы:**

1. Создайте `practice/counter.php`. Обновите страницу 5 раз, затем откройте её в окне инкогнито. Объясните в отчёте, почему счётчики разные.
2. В DevTools (Application → Cookies) найдите `PHPSESSID`. Удалите его и обновите страницу. Что произошло со счётчиком?
3. Найдите файл своей сессии в `C:\xampp\tmp\`, откройте его Блокнотом, сделайте скриншот содержимого.
4. Создайте `practice/theme.php`. Переключите тему, закройте и откройте браузер — тема сохранилась? В DevTools вручную поменяйте значение cookie на `red` — что покажет страница и почему?
5. Создайте `practice/mini_login.php`. Войдите под `student1` / `qwerty1`, затем под `adminka` / `password`. Убедитесь, что содержимое разное.
6. Посмотрите значение `PHPSESSID` до входа и после — оно должно поменяться. Закомментируйте `session_regenerate_id(true)` и повторите. Запишите вывод.
7. Добавьте в `mini_login.php` третью роль `manager` и раздел, который видит только он.
8. Ответьте письменно: почему нельзя хранить роль в cookie?

**Что сдать:** три файла из `practice`, скриншоты к пп. 2, 3, 6 и ответы на вопросы из пп. 1, 4, 8.
